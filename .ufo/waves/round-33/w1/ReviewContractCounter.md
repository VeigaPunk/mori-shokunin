## Findings, by severity

### High

1. **Looser: invalid supported spans do not fail the predicate.** Contract phrase: “each supported row ... span ... of at least 6 words ... located in the committed copy of a new id that row cites” (`contract.md:39-41`; docstring `count-c1.py:20-22`). The validator correctly identifies short, missing and uncited-copy spans at `count-c1.py:271-276`, but merely excludes those rows from `sup` at line 278. The failure condition at lines 284-285 does not require `spans_bad` to be empty. Thus additional invalid supported rows need not prevent passing once ten valid supported rows remain. This is not a failure to restrict lookup to cited new ids: lines 273-275 do restrict it. Recorded controls already demonstrate five-word and uncited-copy survivors (`evidence/c1-controls.txt:6,10`; amendment acknowledgment `contract.md:112-114`); I did not rerun them.

### Medium

2. **Stricter: fenced copies of the decision table also count against uniqueness.** Contract phrase: “exactly one table outside any code fence whose header holds” the four cells (`contract.md:27-28`; docstring `count-c1.py:8-9`). `count-c1.py:153-159` requires both exactly one matching table anywhere and exactly one unfenced matching table. A valid outside table plus an illustrative matching table inside a fence is rejected, although only one is outside.

3. **Both looser and stricter: fence recognition is a toggle, not matching fences.** Same contract phrase, “outside any code fence” (`contract.md:27`). At `count-c1.py:135-149`, any whitespace-prefixed triple backtick or triple tilde flips one Boolean. Opening character, opening length, closing length and valid closing syntax are not tracked. A tilde line inside a backtick fence, or three backticks inside a four-backtick fence, incorrectly changes outside/inside classification. The absence of matching-marker state is direct code evidence; no rendered-Markdown fixture was executed.

4. **Both looser and stricter: URL identity is tested as substring containment.** Contract phrases: a SOURCES row has “a URL” and its Gate row has “that https URL”; the URL is absent at the entering tip and is carried by no other new id (`contract.md:30-34`). The URL-in-source-row check is PRESENT at `count-c1.py:212-213`, but only tests whether the Gate cell string is contained in SOURCES cell 2. It does not establish an exact URL occurrence. Baseline novelty likewise uses substring search over the whole entering file (lines 214-215); cross-id sharing uses substring search in other cited new ids' second cells (lines 233-237). Consequently a shorter URL can be mistaken for its longer-prefix extension; conversely a Gate URL embedded only as part of a different source URL can satisfy the own-row test. This is not a missing-check finding; it is an identity/field-coverage divergence.

5. **Missing: one URL per new id is not enforced.** Contract phrase: “One URL per new id” (`contract.md:60`). `count-c1.py:204-205` takes the first cell beginning `https://`; lines 212-213 require its substring in source cell 2. Neither counts URLs in that source cell or across the Gate row. Pairwise uniqueness at lines 232-240 does not prohibit an individual id from carrying additional URLs. This requirement is explicit in the contract's syntax paragraph, rather than separately spelled out in P-C1's sentence.

6. **Stricter: every mentioned source id must exist, not merely one.** Contract phrase: each row is “naming at least one S### that is a corpus/SOURCES.md row” (`contract.md:28-30`; docstring `count-c1.py:9-10`). `count-c1.py:168-170,184-185` applies `all(...)` to every matched citation. A row naming one registered old id and an additional unregistered old id satisfies the sentence's existential condition but fails the implementation. New ids remain subject to their separate universal registry requirement.

7. **Both looser and stricter: the overlap tokens are not words having four letters.** Contract phrase: “at least 2 distinct words of 4 or more letters” (`contract.md:35-36`; docstring `count-c1.py:16-17`). `count-c1.py:77-78,221,245-246` lowercases and extracts ASCII letters, digits and underscores, then tests total token length. Tokens such as `1234` and `____` qualify without any letters. Non-ASCII four-letter words such as `café` can fail because the ASCII fragment has only three characters. Distinctness itself is correctly enforced by sets.

8. **Stricter: overlap excludes part of the row.** The same contract phrase says “every row ... shares” words (`contract.md:35-36`), without limiting the cells. `count-c1.py:177,243-246` uses only observation plus reading; verdict, sources and any additional columns cannot contribute. This is an extra cell restriction relative to the literal P-C1 sentence, even if observation/reading was the intended location.

9. **Both looser and stricter: digest syntax is not exactly a 64-hex field.** Contract phrase: “a 64-hex sha256” (`contract.md:32-34`; docstring `count-c1.py:13-15`). `count-c1.py:206` selects the first lowercase 64-hex substring anywhere in the Gate row, without token boundaries or a digest-column check. A 65-hex token beginning with the correct digest is not rejected as malformed. Uppercase hex is rejected. Copy and fetch equality use that selected substring (lines 220,224-229), so those byte checks do not correct the field-syntax divergence. The receipt pattern also accepts lowercase only (`count-c1.py:261`).

10. **Looser: admission is an arbitrary prefix, not an admission token.** Contract phrase: “exactly one admit Gate row” (`contract.md:32`). `count-c1.py:192-194` accepts any last cell whose lowercased text starts with `admit`, including `admit-not` or `admitted`. It does not require the token `admit` followed by a delimiter/end. It also identifies these rows by source-id syntax anywhere in the lesson, not by membership in an identified Gate table.

11. **Both looser and stricter: judged-hash line handling differs from an existential physical line.** Contract phrase: “carries a `judged-sha256:` line equal to the sha256 of the entry” (`contract.md:38-39`). At `count-c1.py:261-262`, `\s*` can cross a newline, accepting a key on one physical line and its digest on another. Only the first matching digest is examined, so a later correct hash line cannot satisfy the condition after an earlier stale one. Neither the contract nor the docstring requires exactly one hash line. Independently optional backticks also admit an unpaired backtick.

12. **Stricter: table and registry formatting requirements are unstated.** Contract phrases: “one table ... data rows” and “a corpus/SOURCES.md row” (`contract.md:27-30`). Entry tables need a leading pipe in both header and delimiter, every data row needs a leading pipe, and delimiter cells admit only whitespace, colon, pipe and hyphen (`count-c1.py:141-147`). Every row must have exactly as many cells as the header (lines 167-172). Registry and Gate lines must begin with `|` in column zero (lines 119,192). These are narrower than Markdown table/row syntax; an otherwise equivalent edge-pipe-free table or indented registry table is not recognized.

13. **Error path: a malformed source row can crash instead of reporting unmet.** Contract requires a unique new source row “with status mined” (`contract.md:30-31`); documented counter exits are 0/1/2 (`count-c1.py:33`). A one-cell line `| S180 |` is collected at lines 119-121. With a recognized Gate URL, line 198 records its bad status/shape, but line 212 still indexes `srows[0][1]` without checking length. That path raises `IndexError` rather than reaching `C1=unmet`. This is a static error-path finding, not an executed mutant.

### Low / literal-contract differences

14. **Stricter: “distinct” rows and SKILL lines use an undeclared whitespace equivalence.** Contract phrases: “pairwise-distinct data rows” and “4 distinct lines” (`contract.md:28,41-42`). Row equality uses normalized joined cells (`count-c1.py:164,179-180`); SKILL equality uses normalized lines (`count-c1.py:287`). Lines/rows differing only in whitespace collapse into one. The expressly documented normalization covers quote containment, span containment and R-J matching (`count-c1.py:31-32`), not these two distinctness checks. Case and punctuation differences still distinguish original-counter rows.

15. **Looser: the SKILL target path has no boundary check.** Contract phrase: lines naming “corpus/knowledge/disk-write-rate-r33.md” (`contract.md:41-42`). `count-c1.py:287` checks `ENTRY in l`, so a mention only of `corpus/knowledge/disk-write-rate-r33.md.bak` satisfies the path portion. The Round33 word boundary and twelve-whitespace-token minimum are present; neither substitutes for an exact target-path occurrence.

16. **Stricter under HTML semantics: comments are forbidden as a raw marker, not as comments.** Contract phrase: “holds no HTML comment” (`contract.md:27`). `count-c1.py:129-134` rejects any literal `<!--` anywhere, including an escaped/code-literal example inside a fence that is not an HTML comment in rendered Markdown. This is an extra restriction if “HTML comment” means the markup construct; it matches a stronger raw-marker prohibition. The counter does not otherwise parse HTML.

17. **Looser than “nothing else”: malformed UTF-8 is replaced before containment.** Docstring phrase: text matching collapses whitespace “and nothing else” (`count-c1.py:31-32`; contract `contract.md:58-59`). `count-c1.py:223,253,259-260` decodes copies, dispatch and receipt with `errors='replace'`. Invalid byte sequences can therefore become replacement characters before matching, an additional transformation. Hashes still cover original copy/entry/fetch bytes (`count-c1.py:126,224,228`); the divergence concerns textual containment only.

## Required checks that are present, and boundaries not to misreport

- **Distinct URL and SHA checks are present.** `count-c1.py:232` compares the sizes of both value sets against their dictionaries; lines 237-241 additionally reject cross-source-cell URL sharing. Dictionaries contain successfully parsed Gate ids, but the aggregate requires `gates_ok == len(new_ids)` and matching copy/fetch counts, so omitted bad Gates cannot silently evade the aggregate (`count-c1.py:191-241`). This is over cited S180+ ids, not an independence-of-publishers claim.
- **Quote bounds are present.** `count-c1.py:207-210` requires one through four recognized located quotes, no extra recognized unlocated quote, and an actual whitespace-token count of 3-25 for each. The displayed `(N words)` number and locator filename/range are never validated: the regex captures only quote text (`count-c1.py:50-51,207-210`). Quote containment searches the whole corresponding committed copy (lines 222-225), not the indicated lines. P-C1 literally spells out locator syntax plus copy containment, not a separate truthful-line-number or matching-N test; those metadata limits should not be mislabeled as a missing 1-4 bound.
- **Span location has the correct cited-new-id scope.** `count-c1.py:273-275` searches copies for that row's S180+ citations, not an arbitrary source or uncited copy. Spans need not be one of the Gate quotes: P-C1 says “committed copy,” so whole-copy containment is consistent (`contract.md:40-41`). The high-severity defect is ignoring invalid supported rows at final acceptance, not the lookup scope.
- **Entry hash covers the actual committed bytes.** `show(repo, full, ENTRY)` returns Git stdout bytes (`count-c1.py:55-57,111`); SHA-256 is calculated before decoding at line 126 and compared at line 262. It is not a hash of rendered text, normalized text or the working-tree entry.
- **Coverage and duplicate receipt labels are enforced.** Matching labels are converted to integer row numbers; duplicate numbers increment `dupl`; the exact number set must equal `1..rows_n` (`count-c1.py:264-277`). Missing rows, extra numbered rows and duplicate labels fail coverage. Counts of supported rows are the separate, span-filtered counts at lines 278-285. Unsupported rows need no span under the stated rule.
- **SKILL's stated numerical checks are present.** `count-c1.py:286-290` requires four distinct normalized qualifying lines, `\bRound33\b`, the entry-path substring and at least twelve whitespace-separated tokens. No prose-only, non-comment or unfenced restriction was promised for SKILL lines, so counting such literal lines is not independently a P-C1 violation.
- **Visibility outside the entry is not checked.** SOURCES, Gate, receipt and SKILL scans do not exclude fenced/commented content (`count-c1.py:118-121,188-194,264-287`); entry metadata also counts inside fences (`count-c1.py:127-128`). P-C1 explicitly requires fence exclusion only for the decision table. These are semantic-artifact/receipt-integrity limits, not additional unstated fence requirements.
- **Unstated case tolerances are observable.** Header cells are lowercased, registry status is lowercased, and the admission prefix is lowercased (`count-c1.py:143,193,198`). P-C1 spells the labels in lowercase but does not explicitly define their case policy; record these normalizations without treating case tolerance alone as a demonstrated semantic defect.
- **A1-only conditions are absent by design in this frozen original.** Token-normalized row/observation distinctness and the six-word copied-reading prohibition are in `contract.md:119-123`, not the original P-C1 sentence. Original punctuation-distinct rows and copied Gate readings are documented target weaknesses (`contract.md:115-117`), not proof that the original textual-distinctness check or eight-word check was absent.

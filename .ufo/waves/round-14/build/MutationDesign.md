# Round 14 mutation design — C1 alarm and routing

**Axes:** coverage is primary. Preserve operability (deterministic fixtures and exact roll/exit checks), calibration (no unique-victim or fleet-cause claim), and adjacency (explicit tsukuroi routing) as constraints.

**Scope:** design only, as assigned. No source, fixture, or harness was mutated; no detector was run. The case IDs and outputs below are proposed behavioral expectations, not measurements.

## Grounded gap

- The non-author r13 spotcheck records the rejected-harmed regression: the frozen census emitted `OOM_KILL_JOURNAL crit` and DRIFT, while the delivered structured probe made every kernel-OOM class INFO; the old fleet/non-fleet unit split and tsukuroi owner also disappeared (`corpus/lessons/round-13-verifier-spotcheck.md:77-89,132-134`). It explicitly rejects restoring raw `MESSAGE` parsing.
- The read-time r13 journal implementation has a default `sev=info`, with only user `unit_sigkill_record` promoted to warn, then emits the selected finding (`tools/mori-census.sh:1085-1106`). `unit_failure_record` is described as having “no fleet classification” (`:1101-1102`); the ID mapping has only generic user/system unit-failure IDs (`:1014-1027`).
- Existing `R13_C1_CLEAN_VERDICT` explicitly treats notices as INFO and checks a CLEAN roll; its legacy positive-kill list does not require the repaired OOM alarm or the fleet/non-fleet owner split (`tools/mori-round13-regressions.py:1245-1294`). The nonzero C1 user fixture does not contain positive unit-failure records (`:1072-1081,1168-1187`).
- The initial round-14 spec asks for fleet `UNIT_FAILURE_JOURNAL` warn (`.ufo/waves/round-14/spec.json:14,19`), but L1’s correction supersedes that prompt severity: frozen pre-cutover source emits both `UNIT_FAILURE_JOURNAL info` and `UNIT_FAILURE_OUT_OF_SCOPE info` (`.ufo/waves/round-13/frozen/mori-census.sh:904-908`); OOM is `crit`/DRIFT (`:893-895`), and user SIGKILL alone is `warn`/DRIFT (`:897-899`). The routing cases below therefore expect INFO for fleet unit failures and a CLEAN/rc0 unit-only partition fixture. S035 documents `UNIT_RESULT` on the unit-failure record and `EXIT_CODE`/`EXIT_STATUS` on the process-exit record (`corpus/knowledge/structured-journal-scopes-r13.md:13-14`). The previously observed non-fleet example is `pipewire-pulse.service`, with tsukuroi owning OS triage (`corpus/knowledge/observability-census-r1.md:102-105`).

## Red mutants and independent case oracle

Keep fixture rows and expected tuples as hard-coded test data. Do not derive expected classifications, counts, severities, or roll verdicts from the SUT’s output or source. Pin `_BOOT_ID` to the harness fixture boot; provide structured fields only and no `MESSAGE` query. All unrelated surfaces should be quiet so the expected roll is attributable to the fixture.

### Negative boundary control

`R14_C1_SIGKILL_NOT_OOM` should carry one structured process-exit record (`MESSAGE_ID=98e322203f7a4ed290d09fe03c09fe15`, `EXIT_CODE=killed`, `EXIT_STATUS=9`) and no OOM unit result. Require the existing user `KILL_SIGNAL_JOURNAL / warn` behavior, no `OOM_KILL_JOURNAL`, and DRIFT/exit 1. This prevents the restored OOM alarm from conflating a generic signal-9 record with an OOM cause. Preserve the existing scoped-count, empty-journal/CLEAN, MESSAGE-canary, and error/unavailable controls separately; they measure different contracts.

## Expected detector outcomes (not run)

- Repaired pristine bytes: every listed positive case matches its literal expected finding tuple and roll; the negative control has no OOM finding.
- `MUT_OOM_SEVERITY_DEMOTION_INFO`: the OOM notice case(s) fail on severity and roll (the isolated mutant output is expected to show INFO rather than CRIT and CLEAN/rc 0 rather than DRIFT/rc 1).
- `MUT_UNIT_FAILURE_PARTITION_COLLAPSE`: `R14_C1_UNIT_FAILURE_PARTITION` fails the exact 1/1 bucket and owner assertions. The correct and all-fleet-mutant rolls can both remain CLEAN/rc0, so the detector must compare route tuples, not only the roll.
- `MUT_TSUKUROI_OWNER_OMITTED`: `R14_C1_NONFLEET_OWNER_TSUKUROI` fails its exact owner-token assertion even if the INFO-only roll remains CLEAN/rc 0.
- Frozen r13 bytes should fail the new requirements for the observed reasons in the spotcheck; the existing r13 C1 `CLEAN` expectation must not be reused as the oracle for repaired OOM behavior.

**Evidence/restoration:** no mutation was made, so there are no actual mutant outputs or before/after hashes and no restoration action. The outcomes above are expected detector behavior only; L1’s assigned verifier must measure pristine, mutant, and restored bytes if the mutation battery is run.

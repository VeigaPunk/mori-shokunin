## 1. The r13 gain this repair must keep (baseline facts, from source)

- There are six classes per scope (`tools/mori-census.sh:1034`): `kernel_oom_notice oomd_notice coredump_notice segfault_signal11 unit_sigkill_record unit_failure_record`. That gives 12 tokens across the two rows `SURFACE journal.user` and `SURFACE journal.system` (:1110–1128), and the rows are never summed (:892–893).
- What makes a record count (:927–929): `_BOOT_ID` is a string equal to `$boot`, and `MESSAGE_ID == $id`. On top of that, SIGKILL requires `EXIT_CODE=="killed"` and `EXIT_STATUS` = "9", and SIGSEGV requires `COREDUMP_SIGNAL` = "11". If any record fails, the whole class is refused (`record-invalid`, `boot-mismatch`, `multi-boot`; :926, :991–1010).
- Error paths: rc≠0 (`rc-N`), `timeout`, `stderr-nonempty`, `malformed-json`, `no-timeout-bin` (:941–990), plus missing journalctl, missing jq, or an invalid boot anchor, which make both rows unavailable (:1042–1059). An unavailable class prints `<cls>=unavailable:<reason>` and the scope row becomes `unavailable` (:1115–1119). It never prints a fake 0.
- `--output-fields` never includes MESSAGE (:1068–1072). This matches S014 `:230` as quoted in `corpus/knowledge/structured-journal-scopes-r13.md:22`.
- r13 evidence: 5/5 `R13_C1_*` claims passed, using fixtures of system 2/1/3/3 and user 3/0/1/1 (`mori-round13-regressions.py:119–130`). The live current-boot check matched 12/12, but every value was zero (`.ufo/waves/round-13/evidence/live-measurement.json`). It is not evidence that positive counts work.

## 3. Expected r13 harness flips: semantics migration, not lost counts

Restoring OOM to crit breaks these r13 claims by construction. HarnessMigration owns them. Only verdict and alarm expectations should migrate. The `scoped()` count-token expectations stay byte-identical.

- `R13_C1_SYSTEM_NOTICE_COUNTS`: `primary["rc"] != 0 → fail` (:1129–1130). With system kernel=2, crit gives rc1.
- `R13_C1_USER_SCOPE_NONZERO`: requires CLEAN/rc0 (:1191–1193). With user kernel=3, crit gives DRIFT.
- `R13_C1_CLEAN_VERDICT`: CLEAN is required and `OOM_KILL_JOURNAL count>0` is in the forbidden list (:1273–1294). It also requires `field=user:MESSAGE_ID`, `unit=notice`, `rc=0` and all three `UNMEASURED_CLASSES` names (:1262–1269, :145). If CensusRepair renames the categorical unmeasured reasons, this needs a coordinated update.
- `R13_C1_USER_SCOPE_INDEPENDENT` and `R13_C1_NO_MESSAGE_TEXT` should survive, subject to the CX5 suffix blind spot.
- Selftest :2755–2771 is already expected to DRIFT, but the finding ids and severities (KERNEL_OOM_NOTICE_*, UNIT_FAILURE_JOURNAL info) must migrate. The negative check at :2788 (no `OOM_KILL_JOURNAL|UNIT_FAILURE_JOURNAL` from text-only input) is still valid and must be kept.
- Minor: harness :1112–1113 accepts `boot=unavailable:no-records` for all-zero rows, but the census always prints the validated boot (:1125). The check is weaker than the contract and does no harm. It could be tightened.

## 5. Cross-seat contract conflicts found (for L1)

- **Severity conflict for fleet `UNIT_FAILURE_JOURNAL`.** The JournalRegression prompt says "fleet UNIT_FAILURE_JOURNAL **warn**". The frozen historical bytes emit it as **info** (`git show 6531ac6:tools/mori-census.sh`, the `UNIT_FAILURE_JOURNAL info "...scope=fleet-units"` line). The CensusRepair prompt names no severity. Warn would turn a fleet unit failure from CLEAN into DRIFT, which is a severity drift beyond "restore". L1 should decide this explicitly, and the gate should pin it.
- **Scope extension of the OOM alarm.** The historical alarm was user-journal only (frozen `journalctl --user -b` grep, `scope=user`). The r14 contract adds system scope ("either scope"). That is an expansion, not a restoration, and the lane has recorded before that system-wide OOM counters caused permanent false DRIFT and pulled tsukuroi's OS triage into mori (census :1147–1150). This does not hurt the counters, but NoHarmReview and the judge should record it as a deliberate trade.
- **Resolved by L1 ruling (MoriR14 IRC):** exactly one global `OOM_KILL_JOURNAL` crit line with separate `user_notice`, `system_notice`, `user_unit_oom` and `system_unit_oom` fields and no summed count. DRIFT counts alarm lines, not records. Fleet `UNIT_FAILURE_JOURNAL` is info. A missing, null or array subject goes to `UNIT_FAILURE_UNATTRIBUTED_JOURNAL` info, per scope, with the owner unresolved. My earlier two-row advice, sent to CensusRepair and JournalRegression, is withdrawn. The surviving invariant is "no summed or fake-zero field", not "one row per scope". The first bullet of this section is superseded: fleet `UNIT_FAILURE_JOURNAL` is info.
- **Not resolved: owner of the unit-oom fields.** An oom-kill result on a nonfleet unit sets `user_unit_oom` or `system_unit_oom`, so it raises mori's crit alarm while the same record is also routed `UNIT_FAILURE_OUT_OF_SCOPE owner=tsukuroi`. That is a coherent alarm, not a duplicate count, but the judge should see it named as a trade.

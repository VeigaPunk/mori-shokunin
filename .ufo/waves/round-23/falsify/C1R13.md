## 9. Findings by severity

### F-1 — LOW / informational (predicate weakness, inherited, no observed harm)
**R13 as frozen cannot by itself prove that the receipt-revision existence check exists.**
`record()` asserts only `exit==2 ∧ finding_id==SETUP ∧ stderr==''`; it never reads `error`.

*Concrete counterexample (static, not executed):* delete the two-line existence check at
`tool-prod.py` L172–L173 (the `rev-parse --verify` on `measured`), leaving everything else intact.
For the invalid-revision fixture the flow then reaches L175
`git merge-base --is-ancestor 000…0 <rev>`; git cannot resolve the object and exits **128**, which
is *not* in that call's `ok=(0,1)`, so `git()` raises `Invalid('git_read_failed')` → **exit 2,
`RETENTION_RECONCILIATION_SETUP`, empty stderr — R13 still passes**, with `error` changing from
`receipt_revision` to `git_read_failed`. The sibling requirements do not detect this either:
R01 (valid arm, exit 0) is unaffected, R14 (`diverged`) keeps its own `measured_not_ancestor`
reason, and R25 only inspects `schema`/key presence. So the 26-requirement suite would still read
26/26 with the receipt-revision *existence* check deleted.

*Bound on the damage:* the **observable safety property survives** — an unresolvable receipt
revision is still rejected as a setup error (exit 2), never reconciled and never granted clearance.
What is lost is diagnostic precision (the specific reason) and the ability of the frozen suite to
prove the existence check exists.

*Status at production:* the check **is** present and does fire — `error="receipt_revision"` is
recorded in the committed receipt, and the trace in §5 reproduces it. So this is a gap in
*requirement discriminating power*, not a defect in the implementation.

*Ownership:* inherited byte-for-byte from r22 (`oracle-reconcile-v2.py` L54) and mandated by
`contract.md` ("R01–R24 = the r22 frozen v2 requirements, byte-for-byte predicates except that
R02, R11, R12 read `scanner_unallowlisted`"). Fixing it would require changing frozen bytes,
which the wave forbids. **Not actionable in this wave; recorded as residual risk.**

### F-2 — INFORMATIONAL (R13's own output is not cutover-immune)
R13's arm's stdout changed `schema` v1→v2. The requirement is silent on `schema`, so R13's verdict
is invariant; the change is owned and asserted by R25. Any downstream consumer keying on
`schema` inside a setup-error payload sees a change — intended by C1, covered by R25, and visible
in the same-fixture replay (`c1-replay-entering-08.json` vs `c1-replay-measured-08.json`).

### F-3 — INFORMATIONAL (self-referential digest inside R24, adjacent to R13)
`R24`'s `v['tool_sha256']==FIX.digest(tool.read_bytes())` compares the tool's self-reported digest
with the digest of the file being run — it is self-consistent, not a binding to the production
revision. The binding is established by the driver staging (`stage_bytes(RETENTION_REL, self.revision, …)`)
and is *not* asserted by the oracle. Closed by this seat independently:
staged-after tool sha256 = `4599ee1a…` = production blob sha256 = `git ls-tree` blob
`78c676e665d23a68c571a9d13698a6aae13b1500`. R13 itself is unaffected (its arm never reports a
`tool_sha256`).

### No other findings
No defect found in R13's fixture construction, predicate, tool path, guard, or evidence chain.
`git status` on the lane is clean for tracked files; `git diff seal..production` over
`round-23/frozen`, `round-23/oracle-rename.py` and `round-22/frozen` is **empty** — frozen bytes

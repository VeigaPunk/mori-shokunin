## Findings by severity

### F1 — Medium (evidence strength, not a SUT defect): R16's frozen row is still not branch-proving, and r22's recommended corrections were not adopted

`oracle-rename.py` never reads the `error` field anywhere (grep for `error`,
`allowlist_changed`, `policy_changed` in the oracle: **no match**). A green R16 row
therefore proves only that *some* setup branch fired; it cannot distinguish
`allowlist_changed` from `policy_changed` (R15's arm), from `receipt_revision` failure,
or from any other `Invalid`.

This is the identical defect recorded in r22 by seat `MoriR22.FinalR16`
(`.ufo/waves/round-22/falsify/FinalR16.md`), which recommended (1) pinning
`v.get('error')=='allowlist_changed'` in the R16 predicate and `'policy_changed'` in
R15, and (2) adding a same-repository control chain (measured → G → R1 → R2, identical
argv except `--rev`). **Neither correction was adopted in the r23 frozen oracle**: the
R16 line is byte-identical to r22's and no new fixture variant or control chain exists
in `fixture-builder-v2.py` (whose digest is unchanged, `1b3e16f7…`, so it *cannot* have
gained one).

Smallest counterexample, carried forward and re-derived against the r23 oracle: an
implementation that drops `'allowlist'` from the loop at line 176 and instead requires
the allowlist blob to be canonically encoded would still exit 2 with
`RETENTION_RECONCILIATION_SETUP` on the `allowlist-changed` arm (error
`allowlist_noncanonical`), so R16 stays green while the measured-vs-input byte binding
is gone — the r22 seat's mutant M1, and its identity-substitution variant M2
(comparing against `rev^` instead of `measured_revision`, which the fixture cannot
distinguish because its input revision is exactly one commit after the measured commit).

**Why this is non-exploitable at this revision, and what still stands.** r23 added a
guard r22 did not have: **C21**, a byte-exact source constraint pinning the production
reconciler to the entering baseline plus exactly two transforms (independently
recomputed above). M1 and M2 are source mutations, so both are rejected by C21; C22
separately demonstrates the guard is non-vacuous for added/removed/whitespace-changed
code. Equivalently: because the production source at `f3dc07c` is byte-identical to the
r22 admitted source except for two fragments that do not touch R16's branch, R16's
behaviour here is *provably* the r22 behaviour, and the r22 mutants are unreachable
without failing C21.

What still stands, and is what a reader of the original-26 denominator must carry:
the **frozen requirement row R16 is not self-discriminating**. It is defensible in this
round only because it is conjoined with C21. Any later revision that is not covered by
an equivalent byte-exact guard would inherit an R16 row that cannot distinguish a
setup branch from a byte-binding branch. Recommended (L1 decision, detection-side only,
no fixture change needed): add `v.get('error')=='allowlist_changed'` to the R16
predicate and `'policy_changed'` to R15, and/or add the same-repository control chain.
Until then the honest wording is *"SUT branch holds; oracle row non-discriminating"* —
the same wording the r22 seat used.

## Residual risk (outside R16's power)

1. **The receipt binds no allowlist digest.** The r21 receipt schema carries
   `policy_sha256` but no allowlist digest, so R16 can prove only that the two
   *committed trees* agree — never that the allowlist the scan actually consumed
   matches the one the receipt attests. The tool itself reports
   `receipt_authenticity: 'unattested'` and `privacy_clearance: false`. Unchanged by
   C1; not cured by R25/R26.
2. **R16 proves agreement, not authenticity.** A canonically re-encoded allowlist at
   the input revision (semantically identical, byte-different) is rejected by the byte
   gate, but an allowlist that is byte-identical *and* forged at the measured revision
   is outside R16's reach by construction.
3. **The frozen contradiction in `evidence/frozen-contradiction.json` is C2-only**
   (`CaseEscapedSpace`, mount id 43 / parent 33 vs `/srv` 42). It does not touch C1,
   R16, the source-delta guard or the 26-row denominator. The `exit 1` of the pinned
   driver run is the expected strict red from that contradiction; the C1 rows in the
   same run are independent and green.
4. **Open debt is unchanged** by this falsification: four unallowlisted retention hits
   (raw 95 / allowlisted 86 / non-author 5), original permission RED 11/12, two
   unknown dispositions, baseline acceptance blocked, `privacy_clearance=false`.
   Probe visibility is not clearance.

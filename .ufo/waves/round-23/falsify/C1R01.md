## 4. Why R01 is *entailed* by the guard, not merely observed

R01's four observables are: exit code, stdout-is-a-JSON-object, `finding_id`, stderr.

**(a) `SCHEMA` is write-only.** Static scan of the final source: `SCHEMA` appears at
line 16 (definition) and only as a *dict value* at lines 231 (`check()` return), 274
(`selftest()` return), 287 and 289 (setup envelopes). There is **no** comparison of `SCHEMA`
against anything (`==`, `!=`, `is`, `in`) anywhere in the file. Renaming the literal therefore
cannot alter any control flow, exit code, `finding_id`, or stderr — it can only change the bytes
of one output field.

**(b) The deleted producer is a pure dict entry.** The removed fragment
`'raw_unallowlisted':len(unallowed),` sits inside the returned result dict at (entering) line 234.
It is a read of the already-computed list `unallowed`, which remains live at production lines
219, 220, 221, 222, 224, 226. Deleting it removes exactly one key from the output object and
changes nothing else: `unallowed` is still defined and still consumed; the exit code is
`int(bool(differences))` (line 241) and `differences` is computed at lines 223–230 from
`hits/allowed/unallowed/forbidden/stale/claimed` — never from the output dict. JSON emission uses
`sort_keys=True`, so dict insertion order is irrelevant.

**Consequence:** R01's truth value is *invariant* under both registered transformations. The
measured before=`true`/after=`true` is exactly what the guard predicts, and it is not a
coincidence that could have masked a semantic regression — a semantic regression would have had
to appear in the exit code, the `finding_id`, or stderr, and the guard proves no registered
transformation can touch any of those.

### Concrete counterexample to R01's *sufficiency* (not to its truth)

Because R01 is schema-blind and alias-blind, a tool that (i) reverted the schema literal to
`…-v1`, or (ii) reinstated the exact inverse transformation
`'raw_unallowlisted':len(unallowed),`, would **still pass R01**: neither change touches exit
code, `finding_id`, or stderr. This is a demonstrated limitation of R01, not a defect in the
shipped tool — the shipped tool is pinned by the byte guard (C21) and the cutover itself is
witnessed by R25. But it means R01 must never be cited as evidence for the C1 cutover. It is a
no-harm arm.

## 5. Findings, by severity

### F1 — MEDIUM (verification defect, outside the original-26 denominator): the driver's
### `C22.c1_source_guard_discriminates` check is tautological and cannot fail.

`build/MeasureDriver/measure-round23-v2.py:697-711`:

```python
mutants.append({'mutant': name, 'sha256': sha(data),
                'guard_rejects': bool(data != expected_source)})
...
discriminating = bool(mutants) and all(m['guard_rejects'] for m in mutants)
self.check('C22.c1_source_guard_discriminates', discriminating, ...)
```

`guard_rejects` is computed as *`mutant_bytes != expected_source`*. The three mutants
(`appended_statement`, `removed_line`, `whitespace_only`) are by construction **derived from
`expected_source`**, so the inequality is trivially true for all three. The check never feeds a
mutant through the actual guard predicate (`transform_source()` + the `TARGET_SOURCE_SHA256`
pin), so it would report `discriminating=True` even if the guard were replaced by
`lambda src: src` — i.e. a guard that accepts every source.

I confirmed this by simulation: with a deliberately broken **identity** transform substituted for
`transform_source`, the C22 computation still yields `discriminating=True` for all three mutants.

**Impact is bounded and does not weaken the actual enforcement.** C21
(`measure-round23-v2.py:688`) is the real guard: it requires
`expected_source == retention_after_bytes` **and** `observed_sha256 == TARGET_SOURCE_SHA256`
**and** the frozen `c1-source-delta.json` to agree with the driver's constants. Applying the
real guard predicate to the same three mutants rejects all three (verified by direct
simulation). So the *property* C22 claims is true and independently established by this seat; it
is the *self-test* that is hollow. C22 is a supplementary check (driver `SUPPLEMENTARY_CHECKS`),
outside the original-26 denominator, so C1's 26/26 does not rest on it.

**Concrete correction available to the L1** (not applied by this seat): make `guard_rejects`
evaluate the guard, e.g. `transform_source(mutant) is None and sha(mutant) !=
TARGET_SOURCE_SHA256`, or assert `sha(mutant) != TARGET_SOURCE_SHA256` directly.

### F2 — LOW (reporting honesty, no measurement impact): the 26 requirements rest on 18
### distinct tool invocations, and R01 shares one invocation with eight other requirements.

`oracle-rename.py:33-43` caches by `(variant, receipt_override)`. R01, R02, R03, R04, R12, R22,
R23, R24 and R26 all read the **same** `valid` stdout (nine requirement IDs, one tool run). R11
shares its `forbidden` stdout with R26's forbidden arm; R20 uses a distinct `receipt_override`
(different fixture instance `valid-unsafe`); R21 uses the `symlink` variant. Total distinct
invocations = 18 (8 check-shaped + 10 setup-shaped), confirmed by `len(runs)==18` and
`parsed_runs==18` in both before and after observations.

Consequence: "26/26" is 26 scored predicates over 18 observations, not 26 independent
experiments. This is normal for a re-expressed oracle and is not a defect — but the denominator
must not be reported as 26 independent trials.

### F3 — LOW (documented, not a defect): the oracle's before/after arms are **not**
### same-instance; the same-instance guarantee comes only from the driver's supplementary replay.

The oracle writes fixtures under `out.parent/(out.stem+'-fixtures')`, so the before run uses
`…/c1/before-fixtures/valid` and the after run `…/c1/after-fixtures/valid`. Consequently the
before/after `valid` stdouts legitimately differ in `argv`, `input_revision` and `inputs_sha256`
(receipt bytes embed the absolute fixture path, hence the receipt digest differs). Measured
changed shared keys on the `valid` arm: `argv`, `input_revision`, `inputs_sha256`, `schema`,
`tool_sha256`; removed key: `raw_unallowlisted` only; no key added.

R01 itself is immune to this (it reads none of those five), so R01's before/after agreement is
unaffected. But any *key-for-key* before/after equality claim about the oracle's own runs would
be wrong; the honest same-instance evidence is the driver's C23 replay
(`measure-round23-v2.py:799`), which rewrites `argv[1]` to point at each staged tool and reports
`differences []` and `argv_equal true` for all 18 arms, with the `valid` arm at
`before_exit 0 / after_exit 0`.

(The tool's own recorded `argv` field is `sys.argv[1:]` (production line 241, from
`args.argv_seen`), which excludes the script path — so swapping the staged tool does not perturb
the recorded `argv`, and the C23 `argv` equality assertion is meaningful rather than vacuous.)

### F4 — INFO (residual risk, explicitly not a C1 finding): R26 is a *new* requirement over a

`raw_not_allowlisted` was already produced by the entering tool (entering line 235); only

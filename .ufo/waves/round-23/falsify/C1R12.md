## 1. Verdict

**Bounded agree — R12 is not falsified.** The r23 re-expression of R12 is a *pure, value-identical*
substitution of the r22 predicate; the production schema-v2 tool satisfies it on the frozen `valid`
fixture by direct source trace; and the delivered same-fixture replay shows the three R12 counters are
bit-identical between the entering (v1) and production (v2) tools. No counterexample to R12 exists in
the frozen inputs, the sealed oracle, the production source, or the delivered measurement.

Two material caveats are recorded as findings below and are **not** R12 falsifications: the contract's
declared consequence misattributes one breakage site (§10, F1), and R12's independence is weaker than
the "independent guards" wording implies (§10, F2).

## 8. Falsification attempts (each closed, with the reason)

**A1 — "the substitution weakened R12."** No. In the entering source both keys were the same expression
`len(unallowed)` (L234 of the entering blob), so `raw_unallowlisted` and `scanner_unallowlisted` were
value-identical on every input; swapping one for the other cannot change R12's truth value. §2.

**A2 — "the tool changed something else that R12 depends on."** No. The production blob is byte-equal to
the guard-transformed entering blob (§5), and the same-fixture replay shows only `schema`/`tool_sha256`
differ (§7). `non_author`, `scanner_unallowlisted`, `raw_total` are the same code lines in both blobs.

**A3 — "R12 now reads a key the tool no longer emits (KeyError → silent pass/fail)."** No: `scanner_unallowlisted`
is still emitted (production L234), and the oracle's `record()` wrapper converts a `KeyError` inside the
predicate into `pass=False`, never into a silent pass (`except (KeyError,TypeError,ValueError): ok=False`).
The observed R12 row is a genuine `pass:True` on a parsed JSON object.

**A4 — "R12 is vacuous / passes on anything."** No: it asserts three independent counters plus exit 0,
`RETENTION_RECONCILED` and empty stderr. A tool emitting `non_author=0` (glob not applied), or
`raw_total=6` (NUL blob not skipped), or `scanner_unallowlisted=0` (allowlist over-matched), fails R12.
It is *narrow* (see F3), not vacuous.

**A5 — "R12 might be reading the receipt rather than recomputing."** No in the delivered state: `non_author`
is `len(excluded)` from the rescan (production L226/L236) and `scanner_unallowlisted` is `len(unallowed)`
from the rescan (L234); a receipt disagreeing with the rescan is reported in `differences` and flips the
finding to `RETENTION_RECONCILIATION_MISMATCH`. The *hypothetical* echo-implementation weakness is
inherited from r22 (§10, F3) and is not present in the production blob.

**A6 — "the sealed oracle differs from r22 in ways that affect R12."** No: full diff of
`oracle-reconcile-v2.py` → `oracle-rename.py` shows R12's single-conjunct change and nothing else
affecting R12 (§2).

## 9. R25 (API cutover) vs R12 (unchanged semantic requirement)

- **R12 is an accounting requirement carried over unchanged.** It pins the *values* of three counters
  (`non_author`, `scanner_unallowlisted`, `raw_total`) and the exit/finding contract of the `valid` arm.
  It is blind to the schema string and blind to the alias: it never mentions `schema` and it reads
  `scanner_unallowlisted`, a key that existed at r22 as well. Its verdict is `pass:True` **before and
  after** C1 (delivered evidence, §6), which is exactly what "unchanged semantic requirement" means.
- **R25 is the API cutover requirement** and the only detector of the change: it asserts that *every*
  oracle run whose stdout parses as a JSON object has `schema == "mori-retention-reconciliation-v2"` and
  contains no `raw_unallowlisted` key. It is red at the entering revision (`pass:False`,
  `schema_v2_runs=0`, `misleading_alias_runs=8`) and green at the pin (`pass:True`, `schema_v2_runs=18`,
  `misleading_alias_runs=0`). It is the single flipped row in the 25/26 → 26/26 transition
  (`frozen/c1-requirements.json.before_expected.unmet == ["R25"]`, `after_expected.unmet == []`).
- Consequently: **R12 cannot corroborate the cutover, and R25 cannot corroborate R12's semantics.**
  Any claim that "the C1 requirement set proves the rename" must cite R25 for the rename and the
  value-level requirements (R03/R04/R11/R22/R26) for the semantics; R12 is only one of the value-level
  arms and the weakest one (F3).

## 10. Findings by severity

**F1 — LOW (accuracy of the contract's declared consequence; no effect on R12 or on the measurement).**
`.ufo/waves/round-23/contract.md` ("Declared consequence (not hidden harm)") states that
"r22's oracle-reconcile-v2 R02/R11/R12 **and measure-round22.py's output whitelist** read the old key,
so they no longer pass against tool revisions after C1". The first half is exact: the r22 oracle reads
`raw_unallowlisted` exactly **3** times (R02, R11, R12 — verified by count on the sealed blob) and
those predicates raise `KeyError` against a v2 output, which r22's `record()` converts to `pass=False`.
The second half is **misattributed**: `measure-round22.py:20` lists `raw_unallowlisted` only inside the
`allowed` set, and the check at L26 is a *subset* test, `set(value) <= allowed`. A subset test cannot be
broken by *removing* a key, so the whitelist is inert under C1 and would still accept v2 outputs. The
actual r22 breakage is confined to the three r22 oracle predicates (plus the r22 driver's own oracle
invocation). The declaration overstates the blast radius. Fix: amend the declared-consequence sentence
to name the r22 oracle predicates as the sole breakage site. (No frozen byte may change; this is a
contract-text correction for the next round's knowledge append.)

**F2 — LOW (specification strength; "independent guards" overstates independence for R12).**
`oracle-rename.py` caches tool invocations by `(variant, receipt_override)`; the `valid` variant is
invoked **once** and 12 of the 26 requirements (R01, R02, R03, R04, R12, R22, R23, R24, R26, plus the
`valid` parts of R05–R10 and the `bool-metric` conjunctive arm) therefore read **one** stdout object.
R12 is not an independent observation of the tool; it is a second predicate over the same bytes as R01
and R02. The wave headline "independent guards" is true for the *arms* (18 distinct invocations) but
not for the *requirements within an arm*. Practical consequence: a tool that returns a single
self-consistent but wrong `valid` document can satisfy R12 by construction. Mitigation exists elsewhere
(R03/R04/R22 pin the identities, R24 pins the input digests), so this is a wording/strength note, not a
false green.

**F3 — LOW (inherited from r22, unchanged by C1 — carry forward, do not re-open as a C1 defect).**
R12 is single-arm and counter-only. The r22 attack seat already documented the surviving holes:
`.ufo/waves/round-22/build/AttackR12.md:60-63` — "The oracle's R12 predicate is
`non_author==1 and raw_unallowlisted==1 and raw_total==5` … **Echo SUT.** It copies `non_author` from
the receipt. It passes R12, and no frozen mutant alters `non_author`" — and the wrong-glob variant
(`PurePath.match` instead of `fnmatch`) also passes because the fixture glob is a literal root-level
name. C1 neither introduces nor removes these; the r23 oracle deliberately kept R01–R24 byte-identical
apart from the alias substitution, so this is **inherited debt**, and the honest disposition is to carry
it (open debt), not to treat it as a C1 regression.

**F4 — INFORMATIONAL (measurement-site detail; no defect).**
The oracle's before/after observation files were produced against **two different fixture trees**
(`c1/before-fixtures/*` vs `c1/after-fixtures/*`), so `argv`, `input_revision`, `measured_revision`
and `inputs_sha256` differ between `c1-before-observed.json` and `c1-after-observed.json` for reasons
unrelated to the tool. The guard's `output_pair_normalization` list is sufficient only for a
**same-fixture** comparison — which is exactly what the driver's 18×2 replay receipts supply and what
I verified in §7. Consequence for reporting: a before/after "no other output key or value changed"
claim must cite the replay pair, not the two observation files.

**F5 — INFORMATIONAL (fixture independence of R12's literals).**
`1`, `1`, `5` are hardcoded in the oracle rather than taken from the builder's `expected_*` fields (the
builder exposes `expected_raw_total/expected_excluded/expected_scanner_total` but no unallowlisted
count). They are nevertheless fixture-derivable (§3), so they are independent of the tool — no
self-fulfilling oracle. Recorded so the next round can consider exporting the count as a builder
constant.

**F6 — INFORMATIONAL (guard coverage boundary).**
`C21.c1_source_byte_guard` counts the *exact* alias fragment `'raw_unallowlisted':len(unallowed),` and
requires zero occurrences of the exact SCHEMA v1 literal. A differently-spelled emission of the alias
(e.g. `'raw_unallowlisted': len(x)`) would not be caught by the byte guard — it would be caught by R25
(any occurrence in any parsed stdout) and by the `observed_alias_fragment_count == 0` check only for
the exact spelling. Coverage is complete in combination; no gap.

## 11. Residual risk and verification gaps

1. **R12 is not independently falsifiable by a mutation that preserves the three counters.** Any mutation
   that keeps `non_author=1`, `scanner_unallowlisted=1`, `raw_total=5` while changing, say,
   `raw_not_allowlisted`, `allowlisted` or the identity lists passes R12 — those are covered by R26,
   R04 and R22 respectively. R12 alone is a weak witness; it is one of 26 arms, not a substitute for them.
2. **No mutant was executed for this seat** (static-only item). The byte-identity guard (§5) plus the
   same-fixture replay (§7) make a semantic mutation of the three R12 inputs structurally impossible
   at this pin, so the residual risk of an undetected R12-relevant semantic change is confined to
   *future* revisions that bypass the guard.
3. **The r23 oracle imports the fixture builder across waves** (`.ufo/waves/round-22/frozen/fixture-builder-v2.py`).
   It is sealed and digest-pinned in `seal-manifest.json`, but the dependency is cross-wave and must be
   re-pinned if r22's frozen tree is ever rewritten.
4. **Real-control coverage for R12 is indirect.** The real control (`frozen/c1-expected-real.json`) pins
   the *production* run on the retained receipt (exit 0, `scanner_unallowlisted=4`,
   `raw_not_allowlisted=9`, `raw_total=95`, `allowlisted=86`, `policy_excluded=5`, `non_author=5`,
   `retention_state=red`, `privacy_clearance=false`, schema v2, `raw_unallowlisted` absent). R12 itself
   is exercised only on the synthetic `valid` arm; the real control exercises the same counters on
   real bytes but is not scored by R12.

## 12. What would falsify R12 (concrete counterexample shapes, none realised)

A falsifying counterexample would be any of the following, each of which is absent here:
(a) the production blob differing from the guard-transformed entering blob anywhere other than L16/L234
    (verified: byte-equal); (b) `scanner_unallowlisted` ≠ `raw_unallowlisted` at the entering revision
    (verified: same expression `len(unallowed)`, so equal on every input); (c) the `valid` arm not
    yielding `non_author=1 / scanner_unallowlisted=1 / raw_total=5` under the production source
    (verified by source trace and by the delivered `valid` arm output); (d) exit code ≠ 0, a finding id
    other than `RETENTION_RECONCILED`, or non-empty stderr on that arm (verified: exit 0,
    `RETENTION_RECONCILED`, stderr `""`); (e) a before/after difference in any of the three R12 values
    on the same fixture instance (verified: identical on the shared `valid` fixture across the v1 and
    v2 tools).

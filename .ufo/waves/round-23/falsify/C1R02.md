## 5. Findings

### F1 — Medium — the frozen R02 predicate is a duplicated conjunct; one r22 assertion was dropped

The r22 R02 asserted two *distinct keys* (`raw_unallowlisted==1` **and**
`scanner_unallowlisted==1`). The r23 substitution is a blind token replacement, so the alias
assertion collapsed onto the canonical key and R02 now reads `scanner_unallowlisted==1` twice.

This is faithful to the contract's wording ("pure field substitution; same expected values
1/3/1"), and it is **not a semantic loss**: at the entering revision the alias and the canonical
key were the *same expression* `len(unallowed)` (entering.py:234), so r22's two conjuncts were
already value-identical and r23's single conjunct carries the same numeric content.

What *is* lost: r22's R02 was an accidental **canary for the alias producer's presence and value**
(a tool that dropped the alias key entirely failed r22 R02 with a `KeyError`); the r23 R02 can no
longer fail for that reason, because there is no alias key left to be missing. Alias **absence**
is now owned solely by R25 (and the supplementary `C19`/`C26`/`C23` checks). Consequence for
reporting: R02 must be cited as "pins the in-scope unallowlisted counter to 1 on the valid arm",
**not** as "pins two independent counters". The frozen predicate text is weaker than r22's, and
should not be described as a two-key check.

### F2 — Medium — R02 (and the whole original-26) is observationally blind to a concrete class of counter changes; only the byte guard catches it

Concrete counterexample (source-level, not executed). Mutant **M1**: replace the producer
`'scanner_unallowlisted':len(unallowed)` with `'scanner_unallowlisted':len(scanner)-len(allowed)`.

* M1 is a genuinely different counter in general: the tool's `allowed` list is computed over **all**
  hits (`allowed=[h for h in hits if … in allowed_keys]`), while `unallowed` is computed over
  **scanner** hits only. The two agree only while every allowlist row that matches a hit also
  matches a *non-author* hit — i.e. `allowed ⊆ scanner`.
* On the frozen fixture `allowed ⊆ scanner` holds (the three allowlist rows cover `policy.json` and
  `allowed.txt`, never the non-author `non-author.txt`), so M1 is numerically **identical** to the
  original on every arm: valid → 4−3 = 1 (= `len(unallowed)`), forbidden → 4−1 = 3 (= `len(unallowed)`).
* Consequently **M1 passes R01–R26 unchanged**, including R02, R11, R12, R03, R04 and R26 (M1
  leaves `raw_not_allowlisted`, `raw_total`, `scanner_total` and the hit lists untouched), and it
  also survives the supplementary same-instance replay `C23`, because the *values* it emits are
  equal on the frozen fixtures.
* M1 is rejected by exactly one thing: `C21.c1_source_byte_guard` / `C22` — the byte-exact source
  constraint. This is precisely what the pre-seal amendment claimed for it
  (`preseal-amendment.md`: "a complete syntactic no-other-behavior-delta constraint for this
  mechanical cutover, not a substitute for arbitrary future semantic changes").

**Bounded-agree consequence:** the C1 claim "no other output key, value, exit code or finding id
changes" is **true for the shipped source** (proven byte-exactly in §4) but is **not** provable from
R02 or from the original-26 denominator alone. Any statement that credits R02 — or the 26
requirements as a set — with proving "no other behaviour changed" is over-claiming. The credit
belongs to `C21`/`C22` (source bytes) plus `C23` (key/value/exit/argv equality on one instance).

### F3 — Low — Python bool/int conflation in the oracle predicate

`v['scanner_unallowlisted']==1` is satisfied by a JSON `true` (`True == 1` in Python). No
requirement in the 26 pins the *JSON type* of `scanner_unallowlisted`, so a mutant emitting
`"scanner_unallowlisted": true` would still satisfy R02 on the valid arm. It would not survive the
suite (R11 requires `==3` on the forbidden arm) nor the byte guard, so this is a robustness remark
about the predicate's strength, not an exploitable defect. Same shape applies to the `==3` / `==5`
comparisons in R11/R12.

### F4 — Informational — before/after original-26 arms are not run on byte-identical fixture instances (the scanned inputs are)

The r23 oracle is executed twice by the driver (`C17`/`C18`) against **different** fixture roots
(`…/c1/before-fixtures/…` vs `…/c1/after-fixtures/…`). The fixture builder embeds the fixture's
absolute path inside the receipt wrapper's `argv`, so the **receipt commit** differs between the
arms (valid arm: `18e2af21…` before vs `afa221f9…` after) while the **measured commit that the
tool actually scans** is byte-identical for all 17 variants (`a8e8b5dfb9cc19c66ae3d13f16bee3fa86b36a34`
for the valid arm in both). R02 depends only on the scanned tree, the policy, the allowlist and the
receipt's *semantic* fields, all of which are equal across arms; the differing bytes are the
embedded path string inside `argv`, which the tool uses solely for the path-binding check.

So R02's before/after invariance is sound, but the amendment's "replay before/after tools against
the SAME fixture instances" requirement is satisfied only by the **supplementary** replay
(`C23`, `c1-replay-entering-*.json` / `c1-replay-measured-*.json`, one shared instance). The
original-26 arms should not be described as "same-instance comparisons".

The supplementary replay is where the exact key-set evidence lives. For the `valid` arm
(`c1-replay-entering-00.json` vs `c1-replay-measured-00.json`), the only differing keys of the
parsed output are:

```
{'schema', 'raw_unallowlisted', 'tool_sha256'}
```

with `scanner_unallowlisted == 1` on both sides, identical `argv` (including the fixture path and
`--rev afa221f9…`), identical exit code, identical stderr, and `raw_unallowlisted` present before /
absent after. This is the tightest available statement of the C1 semantic claim, and it matches
R02's content exactly.

### F5 — Informational — R02 does not discriminate the API cutover; only R25 does

`measure4/c1-before-observed.json` and `measure4/c1-after-observed.json`

valid across the cutover; consequently it is *invariant* by construction and carries **zero**
discriminating power about the cutover.

The discrimination is carried by exactly one original requirement, **R25** (`no key
raw_unallowlisted` and `schema == mori-retention-reconciliation-v2` in every parsed run), plus the

## 6. R25 vs. the unchanged semantic requirements (explicit distinction requested)

* **R25 is the API-cutover requirement.** It is the only original requirement that is *new* and
  the only one that is red before the change: "every oracle run whose stdout parses as a JSON
  object has `schema == mori-retention-reconciliation-v2` and no key `raw_unallowlisted`". Its
  before-state is red by construction (`frozen/c1-requirements.json` →
  `before_expected.unmet == ["R25"]`, `before_expected.misleading_alias_runs == ">0"`), and its
  after-state is green (`after_expected.unmet == []`, `misleading_alias_runs == 0`). R25 is
  red-before/green-after and therefore the *only* original-26 member with cutover-discriminating
  power.
* **R01–R24 are the unchanged semantic requirements.** Their predicate bodies are byte-identical
  to r22's except the R02/R11/R12 field substitution, they are green before *and* after, and they
  certify that the cutover did not move the arithmetic, the identities, the exit codes or the
  finding ids. R02 belongs here, with the F1 qualification.
* **R26 is a new, non-cutover requirement** (independent recount of `raw_not_allowlisted` from the
  fixture's committed policy/allowlist bytes on the `valid` and `forbidden` arms). It pins the
  *other* half of the renamed pair — the field whose semantics the misleading alias used to
  suggest — and it is green before and after, which is the correct behaviour for a semantic
  requirement.
* Consequence for the C1 claim as stated in `contract.md`: "Before→after for C1 is measured by the
  r23 oracle only" and "Requirement passes before expected 25/26 (R25 red), after 26/26" are both
  confirmed by the committed evidence and, for R02 specifically, by the independent static
  derivation in §3.

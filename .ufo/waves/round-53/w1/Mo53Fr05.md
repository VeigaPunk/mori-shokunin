  `si_mem_available()` (v7.3:33-73), so no row disposition changes; the summary is incomplete, not
  wrong. Suggest the L1 extend that cell when editing the entry.
- LOW — "64 changed lines" for `Documentation/admin-guide/sysctl/vm.rst` is the count of the stated
  command `diff -u … | grep -c '^[-+][^-+]'`, which skips blank added/removed lines and the two
  diff headers. The real delta is 83 changed lines (64 added content + 16 added blank + 2 removed
  content + 1 removed blank), and the inserted `panic_on_unrecoverable_memory_failure` section alone
  spans vm.rst.v7.3:926-1004. Same method gives 22 for `mm/show_mem.c` (no blank +/- lines there), so
  the table is internally consistent with its own stated method — a presentation limit, not a data
  error. If the L1 wants the number to read as "lines touched", the stated command should change
  (routed item, round 54).
- LOW — `vm.rst` v7.3 drops the pointer "Default values and initialization routines for most of these
  files can be found in mm/swap.c." (vm.rst.v7.2:22-23 deleted). The per-knob default statements
  survive (`admin_reserve_kbytes defaults to min(3% of free pages, 8MB)`, vm.rst.v7.3:88;
  `user_reserve_kbytes defaults to min(3% of the current process size, 128MB)`, vm.rst.v7.3:1116), so
  my rows 19 and 23 are unaffected. Any other lane claim that points at mm/swap.c for these defaults
  must be re-pinned before it is quoted at v7.3 (not in my block; routed to the L1).
- LOW — line numbers moved in **both** directions in vm.rst between the two copies
  (`admin_reserve_kbytes` 84 → 82, `overcommit_kbytes` 825 → 823, `user_reserve_kbytes` 1029 → 1106).
  A re-pin that copies v7.2 line numbers will be wrong in two ways; the ledger's own SOURCES rows
  (S503 `si_mem_available lines 33-73`, S507 `admin_reserve_kbytes 82-109, overcommit_kbytes 823`)
  are correct for v7.3 — I checked both against the copies.
- LOW — standing wording nuance for round 54 (not a v7.3 change, does not alter any disposition):
  row 13's claim says the low watermark is summed "over every memory zone of the machine", while
  `for_each_zone()` covers only **online** nodes' zones (include/linux/mmzone.h v7.3:1801-1804 +

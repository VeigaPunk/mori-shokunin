## What in the v7.2→v7.3 diff a careless reader might miss (per row)

- Rows 1–5 (proc.rst, 3 changed lines total): neither changed line is in the meminfo definitions. One is a
  prose typo fix in the THP/PSS accounting paragraph (v7.3:516 `…if any page of the larger allocation`,
  v7.2 had `any page page of the larger allocation`); the other adds one line to the `/proc/pid/maps` flags
  table (v7.3:611 `ur    userfaultfd read-write-protect tracking`). The added line shifts every later line
  down by one, so `MemAvailable` moves 1126→1127, `CommitLimit` 1220→1221, `Committed_AS` 1238→1239, and the
  `meminfo` heading 1042→1043. The meminfo section text itself is byte-identical. A reader who compares
  line numbers across the two copies will see a "shift" and may mistake it for a change of the definitions.
- Rows 6–8 (meminfo.c): the file is byte-identical between v7.2 and v7.3 (same sha256
  `d6c5807421a69eac21efd737b39d099c711b3132b371dc34986d181746e3deda`), so no row in this block can change
  for any reason in this release. The three quotes are not literal byte strings of the file: they are the
  whitespace-collapsed forms of two-line spans (rows 6 and 8 span a source line break) and, for row 7, of
  the two-line helper body.
- Row 7 specifically: the quote cell contains a literal backslash-n (`" kB\n"`). It matches the C source
  byte-for-byte as written, and `count-c1.py`'s whitespace collapse leaves the escape untouched, so the
  frozen counter is unaffected. The trap is for any future re-implementation that interprets `\n` as a
  newline before searching — it would not find the quote and could wrongly conclude `absent`.
- Rows 9–10 (mm_inline.h, ledger count 49): the real diff is 53 deleted lines — the whole uffd-wp pte
  helper `pte_install_uffd_wp_if_needed` with its comment block, v7.2 lines 569–621 — plus 2 changed
  lines in `num_pages_contiguous` (`memdesc_section(cur_page->flags)` →
  `memdesc_section(&cur_page->flags)`, mm_inline.h.v7.3:600 and 610, replacing v7.2:653 and 663). The
  ledger's change table names only the uffd-wp removal, so the `memdesc_section` edit is invisible in its
  description even though it is half the non-uffd part of the diff. `folio_is_file_lru` (lines 13–31) is
  byte-identical. This block is the only place in the ledger's nine files where a v7.3 change touches
  userfaultfd machinery — relevant to the lane's frontier, not to these claims.
- Rows 11–12 (show_mem.c, 22 changed lines): the eight diff hunks are at v7.2 lines 16 (new
  `#include "page_alloc.h"`), 116 and 177 (`nodemask_t *` → `const nodemask_t *` parameters), 306/320/347
  (printk format-string edits, including `%luKB` → `%lukB` for `reserved_highatomic`/`free_highatomic` and
  `%ukB` → `%lukB` for `local_pcp`, plus a `K((unsigned long) …)` cast), 397 (`"%ld total pagecache pages"`
  → `"%lu total pagecache pages"`) and 426 (`"%lu pages hwpoisoned"` → `"%ld pages hwpoisoned"`). None
  lands inside `si_mem_available` (v7.2 32–72 == v7.3 33–73, byte-identical); the offset of the function
  by one line is caused only by the new include. The printk edits are, however, inside `show_free_areas`,
  which `__show_mem` calls, and `__show_mem` is what the global OOM kill report prints
  (mm/oom_kill.c `dump_header` → `__show_mem(SHOW_MEM_FILTER_NODES, …)`) — see the routed item below.

## Cross-checks that bear on the ledger beyond this block

- The ledger's "What changed" table was re-derived from the committed copies with the table's own stated
  formula (`diff -u <v7.2> <v7.3> | grep -c '^[-+][^-+]'`): proc.rst 3, meminfo.c 0 (byte-identical),
  mm_inline.h 49, overcommit-accounting.rst 0 (byte-identical), vm.rst 64, util.c 14, mman.h 0
  (byte-identical), mmap.c 190, show_mem.c 22. Every number in the table matches — the table is
  reproducible exactly as documented. But the formula itself undercounts: `^[-+][^-+]` also rejects a
  changed line whose *content* starts with `-` or `+`, so blank changed lines (diff line exactly `-` or
  `+`) and RST underline lines (`+-------`) are dropped. Counting every changed line instead gives
  proc.rst 3, meminfo.c 0, mm_inline.h 57 (49 by the formula; 8 blank lines omitted), vm.rst 83 (64; 17
  blank + 2 marker-prefixed omitted), util.c 14, mman.h 0, mmap.c 205 (190; 15 blank omitted), show_mem.c
  22. The table's numbers are self-consistent and no claim disposition depends on them, so this is a
  method caveat for the L1, not a data error — see the finding below.
- The ledger's reading-rule pointer `mmap.c.v7.3:563-571` is correct: v7.3:563–571 is exactly the
  `if (flags & MAP_NORESERVE) { … }` block with the two `vma_flags_set(&vma_flags, VMA_NORESERVE_BIT);`

  corroborated from upstream: `include/linux/mm.h` defines `DECLARE_VMA_BIT(NORESERVE, 21)` identically at
  v7.2 (line 322) and v7.3 (line 323), so `VMA_NORESERVE_BIT` is the same bit the legacy `VM_NORESERVE`
  named; the mmap.c respelling is an accessor change, not a policy change.

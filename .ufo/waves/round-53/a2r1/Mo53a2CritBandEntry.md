# Mo53a2CritBandEntry — residual review of 34d97cd3eaea8c13b0f065afc52aac1e5cf518a5

## Counterexample and evidence

Reviewed the requested entry and `SKILL.md` Round53 section against the committed v7.2/v7.3 source copies and the contract's S499–S514 references. Read-only evidence below is from the copies in `corpus/evidence/sources-r53/` and `corpus/evidence/sources-r52/`.

1. **Two-sided signed-delta band is bounded too absolutely.** The entry says: “Each CPU holds a signed local delta below one batch … so the global part differs from the exact sum by less than one batch per CPU, in either direction.” The signed direction is sound in the ordinary batching case: `percpu_counter_add_batch()` flushes when `abs(count + amount) >= batch` (`percpu_counter.c.v7.2:93-112`, fallback `:120-135`), and `percpu_counter_read_positive()` reads the global count and clamps negatives to zero (`percpu_counter.h.v7.2`, relevant implementation). But the text makes this a generally applicable per-CPU bound, while its own later CPU-hot-add exception means the batch may no longer be the batch-sized bound for every present CPU. More importantly, the quoted per-CPU counter algorithm permits a single `amount` whose magnitude is already at least `batch`: the slow path folds the whole amount into global state, not a locally bounded delta; this preserves a post-operation deviation bound only if the pre-operation deviation is within the invariant, not a universal claim about arbitrary intermediate/read timing. The safe statement should bind the result to the stable configured batch and ordinary completed updates, and explicitly exclude topology transitions / concurrent reads. Replacement: “With a stable batch and outside topology-transition races, the completed per-CPU updates keep each local delta within the batching bound; signed deltas can put the global read on either side of the exact sum. The tool’s `batch × CPUs` value is a conservative model, not a universal instantaneous bound.”

2. **CPU hotplug characterization has a stronger counterexample than the entry names.** Entry says: “CPU hotplug does not [recompute the batch] — a dying CPU only folds its delta into the global count.” In source, `percpu_counter_cpu_dead()` first calls `compute_batch_value(cpu)` (`percpu_counter.c.v7.2:266-283`), which recomputes the generic `percpu_counter_batch = max(32, num_online_cpus()*2)` (`:258-264`), then folds each counter's dying-CPU delta. Thus the categorical statement “CPU hotplug does not” is false for the generic batch. However, that computation does **not** update `vm_committed_as_batch`, which is the distinct batch passed by `mman.h.v7.3:76-78` to the committed-memory counter; so the relevant conclusion is only that CPU hotplug does not recompute this *VM-specific* batch. The CPU-hot-add stale-batch concern is plausible, but evidence for online notifier add/recompute behavior is absent from the quoted counter source (it only shows the CPU-dead callback). Smallest safe replacement: “CPU-dead handling recomputes the generic `percpu_counter_batch` and folds that CPU’s deltas, but it does not call `mm_compute_batch()` or update `vm_committed_as_batch`; the cited evidence does not establish the CPU-hot-add callback path. Do not imply that all percpu-counter batching is unchanged on hotplug.” Also soften “After a CPU hot-add the batch stays sized for the old CPU count” to “The cited `mm_compute_batch` call sites do not recompute this VM-specific batch on CPU hot-add; this review did not establish whether another call path does.”

3. **“only memory hotplug and sysctl writes” omits initialization.** The entry says: “Memory hotplug and a write of the overcommit sysctl recompute the batch.” `mm_compute_batch_init()` calls it at init (`mm_init.c.v7.2:226-233`), in addition to the memory notifier (`:212-224`) and the policy handler (`util.c.v7.2:806-834`). Any wording that implies these are the only call sites is inaccurate. Replacement: “The source shows an init-time computation, recomputation on memory online/offline, and recomputation in `overcommit_policy_handler` when the policy value is written.” The paragraph should distinguish this from CPU dead's generic batch refresh.

4. **Mode-0 cap needs kernel-unit and checked-request qualification.** The entry says: “only one request larger than RAM + swap is refused.” `__vm_enough_memory()` mode 0 compares `pages > totalram_pages() + total_swap_pages` (`util.c.v7.2:972-975`), and `vm_acct_memory(pages)` occurs before this check (`:964`). This is a per-request overcommit-accounting test, not a general guarantee that only one kind of allocation can fail, nor that a request at/below the cap succeeds (other failure mechanisms remain). The direction is “larger than” (strict >), but label “only one request” is imprecise. Replacement: “In mode 0, this commit-accounting check rejects an individual request only when its page count exceeds total RAM pages plus total swap pages; this says nothing about other allocation failure causes.” Apply to both the entry’s table and SKILL row 1184; preserve `single_request_cap_kb` as tool-field label, not as an unrestricted kernel guarantee.

5. **Reserves: reserve subtraction is a modeled worst case, not a universal enforced amount.** Entry table says `usable_kb = CommitLimit − Committed_AS − admin_reserve_kbytes − user_reserve_kbytes`, while correctly noting the strictest caller and per-process cap. Kernel source subtracts admin reserve only when `!cap_sys_admin` (`util.c.v7.2:978-984`) and subtracts `min(mm->total_vm / 32, user_reserve)` only when `mm` is non-NULL (`:985-992`). Thus `usable_kb` is not the actual allowance for every request/process: admin-capable callers retain admin reserve; kernel/no-mm callers do not incur user reserve; smaller `total_vm` pays less than the full user reserve. Entry's “both reserves” is acceptable only if explicitly kept under its existing model qualification; the preceding prose says it reports usable_kb without that qualification until later. Replacement: “The tool subtracts both full configured reserves as a conservative model for a non-admin caller with a sufficiently large `mm`; the kernel’s actual allowance is caller- and `mm`-dependent (`admin` only for non-admin; user reserve is `min(total_vm/32, configured reserve)`, and absent when `mm == NULL`).”

6. **S514 claim is narrowly supported but its label can overstate scope.** Entry says: “the batch rule is unchanged at v7.3” and cites byte-identical `mm_compute_batch` ranges. The evidence supports only that the selected function body is byte-identical between the two copies, not that the overall batching/read/refusal rule or all relevant call sites are unchanged. It also compares ranges whose line offsets differ by four; “byte-identical” should name the compared function body rather than ranges as if the entire files/functions surrounding them were identical. S514 is an mm_init.c copy only; no v7.3 percpu-counter or `util.c` copy is listed. Replacement: “S514 confirms that `mm_compute_batch()`’s function body is byte-identical in these v7.2/v7.3 copies; this does not recheck the per-CPU add/read implementation, refusal path, or call-site behavior at v7.3.” Apply in the entry boundary and avoid implying S514 demonstrates the complete rule unchanged.

7. **Band consequences risk implying next-request result is determined by signed-delta sign alone.** Entry says: “with net-negative local deltas a non-root allocation can be refused while they still show room, with net-positive deltas the kernel can admit past them.” The sign intuition matches `global = exact - sum(local)`, but actual admission also compares caller-specific `allowed`, request size, and current updates; the strict check accepts when global read is `< allowed` and otherwise refuses (`util.c.v7.2:978-1002`). Phrase as counterexample possibility, not a predictive outcome. Safe replacement: “Near the boundary, signed local deltas can make the global-only comparison differ from the exact-sum comparison in either direction; the caller-specific reserve and request size still determine the actual check.”

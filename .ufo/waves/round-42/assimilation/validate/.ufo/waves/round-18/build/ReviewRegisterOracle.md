# C2 register review — round 18

## Axes
- **Oracle fidelity:** whether each frozen external ruling preserves the closure's full judgment.
- **Chronology determinism:** whether the verdict is defined for Git history shapes and path lifecycle events.
- **Correction integrity:** whether later labels can change the measured result without evidence.

## Findings (severity order)

### High — `r17-C3` loses the closure's partial qualification

`.ufo/waves/round-18/frozen/c2-register.json:24-29` records `r17-C3` as `outside_ruling: "co-evolved"`. The cited non-author ruling is more qualified: the earlier witness and miss/hit+sibling oracle preceded the final tool change, while expanded candidate/control pins and the tool revision were co-committed; the evidence supports the calibration repair but **not blanket pre-build preregistration of all final controls** (`corpus/lessons/round-17-verifier-spotcheck.md:207-213`). The closure repeats the explicit instruction not to label the round pre-build (`.../round-17-verifier-spotcheck.md:398-402`). Thus `co-evolved` is a safe coarse proxy for “not established as pre-build,” but is not a faithful encoding of the ruling's partial status unless the schema explicitly gives it that meaning. The current schema does not (`c2-register.json:4-14`).

By contrast, `r17-C1`'s `co-evolved` matches the ruling that the table and implementation were co-committed and later changed together, which is meaningful final-patch evidence rather than a demonstrated pre-build freeze (`c2-register.json:16-19`; lesson `:120-130`). `r17-C2`'s `co-evolved` also matches the ruling that the initial tool/harness were co-developed, both changed together, and the assertion universe was not proven frozen before initial implementation (`c2-register.json:20-23`; lesson `:169-172`).

**Precise fix:** keep the frozen JSON unchanged. Add an append-only correction to the new `corpus/evidence/freeze-register.json` (the correction file named by the frozen `label_rule`, and absent in this checkout when read) setting `r17-C3`'s external ruling to `partial`, with the cited lesson ranges and a reason. Define two distinct comparisons in the correction semantics: exact-category agreement, and the coarser proposition “pre-build is substantiated.” A binary filesystem verdict of `co-evolved` can agree with the latter for a `partial` oracle, but must not be reported as exact agreement with `partial`. Report partials separately so the contract's 3/3 oracle-agreement claim cannot conceal loss of qualification (`contract.md:31-37`).

### High — `label_rule` lets an unsupported correction erase an overclaim

The rule says the label of the last row wins, then counts an overclaim only when that effective label is `pre-build` and the computed verdict is not (`c2-register.json:13`). It imposes no correction evidence, allowed-transition, external-ruling-consistency, ordering, or revision-binding requirement. A later row can therefore relabel a `pre-build` overclaim to `co-evolved`, `partial`, or another value and make the overclaim disappear even if that label is unsupported. The independent `oracle_disagreement` calculation does not prevent this: it is reported separately and does not invalidate the correction or preserve the original overclaim.

**Precise fix:** in the append-only correction file, require every correction to identify its claim, prior effective row, new enum value, rationale, cited independent evidence, and the commit/revision (or content digest) at which it becomes effective. Reject rather than apply a correction that contradicts the applicable outside ruling; retain the prior effective label and count it as uncorrected. Preserve and report both the original declared-label result and the corrected-effective-label result. For `r17-C3`, `partial` must be an allowed explicit label and supported by the non-author ruling; an unsupported replacement must not reduce the count. Bind the correction snapshot to the measured revision, so a later appended row cannot retroactively change an earlier run. These are appended semantics only; do not edit the frozen register. The correction CLI is already an explicit input in the contract (`contract.md:62-65`).

### High — merge ordering is not a causal ordering

`R` is defined as `git rev-list --reverse --topo-order <base>..<tip>` and the verdict compares whether `L` “precedes” `I` in `R` (`c2-register.json:5-10`). Topological output is a linear serialization of a DAG, not a causal total order: commits on divergent branches are incomparable, and their relative output order does not establish that the frozen change preceded the implementation change. In addition, only `I` explicitly says its diff is against the first parent; `L` does not specify merge-diff semantics (`:6-7`). A merge diff invocation that omits merge handling can miss merge changes, while comparing different parent sets can produce different touched-path sets.

**Precise fix:** define one merge policy for both `I` and `L`. The simplest deterministic policy is to require `base` on `tip`'s first-parent chain, traverse `git rev-list --first-parent --reverse`, and define every commit's delta—including merges—as the resulting tree versus its first parent. Use an explicit parent-to-commit diff (and the empty tree for a root, if roots are admitted), not implicit merge defaults. Then order is the first-parent chain. Alternatively retain the full DAG but call a ruling `pre-build` only when every relevant frozen-path change is a strict ancestor of every earliest implementation-path change; same-commit or incomparable events must not count as pre-build. If the base is not an ancestor under the chosen policy, return an explicit indeterminate/out-of-window result, not a guessed order.

### Medium — path operations and base contents need explicit semantics

The register asks about exact paths but does not define rename or interrupted-path behavior (`c2-register.json:4-10`). With rename detection off (`diff-tree` without `-M`), a rename is represented as deletion of the old path plus addition of the new path. That is deterministic for exact path-set matching, but the rule does not say whether a rename is a change to both path identities or one logical artifact. Also, `absent` checks only whether the path exists at `tip`, while `L` uses only the last touch. A path deleted and then re-added is therefore not absent; its final re-add becomes the chronology event, even if the path was unavailable in between. That may be intended, but currently is unspecified. Finally, “all frozen paths exist at base” (`:7-9`) treats mere path presence as an earlier freeze, even if the content was not fixed there or an implementation path already existed before the measured range.

**Precise fix:** explicitly make matching path-based and disable rename detection, counting both source deletion and destination addition as touches; or explicitly enable rename detection and count both endpoints. State that a deleted/re-added path is a new freeze event and that any interrupted interval invalidates continuous-freeze status; if identical-content restoration is to preserve an earlier freeze, require a recorded blob/content digest and evidence of that earlier snapshot. Bind frozen path content to the base blob IDs/digests. Require the base to be a verified pre-implementation boundary (e.g. implementation paths absent at base, or independently establish their first introduction); if implementation already exists at base, return `out-of-window`/`indeterminate` rather than treating later edits as its first implementation or inferring pre-build from frozen-path presence. Distinguish `no implementation-path change in the measured window` from “no implementation.”

# C2 critique — MoriR20.C2Critic

## Bottom line and axes

**The 14→0 count is defensible only as capability acquisition, not as 14 production defects fixed.** C2 says the entering tool is absent and explicitly says the 14 cases are not historical defects (`contract.md:90-93`); it then requires 14/14 finite oracle matches (`:93-104`). If that is the only credit claimed, it is not a free lunch: it records one bounded new capability exercised against 14 synthetic requirements. It is a metric freebie/overclaim if used to imply a 14-item reduction in real fleet failures or that operators now know every seat's runtime outcome. **Impacted axes:** coverage (legitimate narrow advance), calibration/claim integrity (do not turn cases into defect counts), operability (live semantics still have gaps).

## Findings

1. **Live r19 is freshly recountable from retained files, but the original “16” has no count-specific independent provenance.** The traceable source is the hand-written `.ufo/waves/round-19/wave1-settlement.json`: it records 64 returned IDs and lists 16 `reports_present` names (`:2-23`); the author-side closure report, authored by `mori19attempt2`, repeats “Sixteen reports remain” and cites that receipt (`.ufo/reports/round-19/mori.md:1,52-56`). The fleet MANIFEST does name `CloseMori19` as non-author integrator and `CloseMori19.C2Count` among independent reviewers (`MANIFEST.json:10149`), and its closure repeats W1 64/16 (`:10171`). But its enumerated independent rechecks are finite C1/C2 case counts and oracle parity (`:10151`), not a command/source for independently recounting W1 reports. **[INFERENCE]** The record does not establish who independently counted the 16 or bind that recount to a contemporaneous tree snapshot; closure repetition is not by itself source independence.

   There is a useful *current* independent filesystem recount: `wave1-run.json` has 64 task-call members (`DraftProvince.md:18-20`; the JSON query `.taskCall.tasks|length` returned `64`), and read-only `stat -c '%n %s' .../.ufo/waves/round-19/build/*.md` returned 16 files, all nonzero. The names match the hand-written list. This establishes 16/64 in the tree as inspected, not that a new tool ran, nor that this is the exact closure-time snapshot. The production `tools/` listing did not contain `mori-wave-settlement.py`; the reviewed implementation was only a build candidate. **No live scan or tests were run.**

2. **A schema match does not prove a dispatch occurred.** Discovery is every `*.json` with `schema == ufo-swarm-wave-dispatch-v1` (`contract.md:64-69`); the candidate trusts that schema and the embedded `taskCall` (`build/ImplSettlementAlt/tools/mori-wave-settlement.py:131-148`) without matching an invocation/returned-ID receipt. Thus a valid preflight/archive JSON with that schema and a non-null taskCall but no actual task call is counted as a wave; its members can show missing, or even settled if old files already occupy their paths. The tool can observe a *declared manifest*, not authenticate “dispatched seats.” A concrete local near-miss is `.ufo/waves/round-16/wave1-context-corrected-not-dispatched.json`; it is a `ufo-swarm-wave-v1` plan, so the current exact-schema filter correctly ignores it. Do **not** claim that file itself is miscounted. It demonstrates why the filename is not enough; the remaining gap is that an undispatched file with the accepted dispatch schema is indistinguishable from a real dispatch.

   **Smallest safe boundary:** either bind each counted wave to an authoritative dispatch/return receipt, or label results explicitly as filesystem status for *declared taskCall entries* and avoid asserting actual dispatch authenticity. The latter is a valid read-only tradeoff; it is not evidence of runtime completion. A claim that this scan alone identifies every actually dispatched seat should be rejected.

3. **Cleanup and relocation collapse into “missing” or “empty”; this is a snapshot, not a completion history.** C2 intentionally defines only path shape/size and says missing is not dead (`contract.md:74-81`). It has no record of whether a report was never written, deleted later by hygiene, moved, or truncated. The lane's own round-12 lesson says the “wave-settlement hygiene interference” candidate was rejected/deferred and **not yet measured by the census** (`corpus/lessons/round-12.md:109`); therefore actual hygiene deletion is not established here. But if a report is deleted after closure, this scan will report `missing`; if emptied, `empty`—exactly the same observation as never-written/empty-at-scan. The design note also acknowledges this structural limit (`build/DraftProvince.md:26-27`). A scan over all historical dispatch files has no time/round filter, so one old cleaned report can keep aggregate exit 1 indefinitely.

   A renamed report directory has the same issue: tasks retain the original `Report:` trailer path, and the specified output has member names/statuses but no expected path (`contract.md:70-76,82-85`). A move from the declared directory to a new one will therefore appear `missing` at the old path, with no “moved” diagnosis. This is not hypothetical path ambiguity in the surrounding evidence: a round-17 audit records same-name wave-1 reports under `build/advice` that were not falsify-wave deliveries (`.ufo/waves/round-17/build/WaveRegistryVsReports.md:32-35`). Correctly refusing to count a different wave is important; however, the output should expose the safe relative *declared* report path so an operator can diagnose relocation. Keep such files not-settled unless an explicit relocation/receipt rule authorizes them.

   **Tradeoff, not a parser fix:** with no retained cleanup or dispatch receipt, distinguishing deleted-after-success from never-written is impossible from filesystem state alone. Keep `missing` neutral, label it “missing at declared path as of scan,” and do not promote it to failed/dead/killed. If closure history must be proved, preserve separate append-only completion/cleanup evidence; do not pretend this scanner has it.

4. **Fixable false-green in the visible candidate: absent `taskCall` becomes `no-spawn`.** Contract only grants `no-spawn` for `taskCall: null` (`contract.md:68-69`). The candidate uses `document.get("taskCall")` and treats any `None` as `no-spawn` (`ImplSettlementAlt/tools/mori-wave-settlement.py:136-148`, `_wave_state` `:118-128`). Therefore a dispatch-schema JSON with the `taskCall` key omitted is accepted as no-spawn and can contribute exit 0. Missing/malformed taskCall is not the explicit null case. Require the key and exact supported shape; reserve no-spawn for explicit null; classify malformed/missing shape as unavailable/unreadable and non-green. Add a frozen case for it.

5. **Fixable per-seat false-green: duplicate report paths (and stale files) are not bound to members/attempts.** The candidate evaluates each task independently (`:80-115`) and settles when every member's status is present (`:118-128`); neither contract nor 14 frozen cases require unique paths (`c2-expected.json:7-20`). Concrete counterexample: two members whose final trailers both name the same existing nonempty `X.md` are both marked present, so the wave can be `settled` with one report for two seats. Similarly, any pre-existing nonempty file at a reused attempt path passes: the checker does not establish that the file was created for this dispatch. Reject duplicate safe report paths (and, if repeated attempts reuse paths, require attempt freshness/receipt binding or report “path present, provenance unverified”). Add duplicate-path and stale-report fixtures before claiming per-seat completion.

## Smallest safe correction

- Keep `14 capability_absent → 0` and `14/14 matched` separate: one missing capability before, bounded synthetic behavior after; never phrase as 14 fixed production defects.
- For live r19, record the tool's actual output only after it exists and runs. Bind the 64 denominator to a dispatch receipt and the 16 current paths to an as-of snapshot; identify the counter/source. Do not call the existing hand-written receipt an independent tool reproduction.
- Label discovery as declared manifests unless actual dispatch evidence is checked. Reject missing `taskCall` as malformed, reserve `no-spawn` for explicit null, and enforce unique report-path/member binding; extend the oracle for these cases.
- Return a safe lane-relative expected path per member and phrase absent status as `missing_at_declared_path`. Preserve “unknown cause” for hygiene deletion/movement; require separate retained evidence if the product claim needs historical completion or dispatch authenticity.

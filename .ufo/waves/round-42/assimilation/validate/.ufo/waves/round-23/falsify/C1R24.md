## 5. Concrete counterexamples (CE-1 … CE-5) — why a green R24 proves little

Static derivations against the frozen fixture and the frozen predicate; **not executed** (my item
authorises static analysis only). Each is a tool that scores **26/26** on the r23 C1 oracle while
violating what R24's predicate appears to assert.

**CE-1 — `input_revision` is unfalsifiable in the synthetic suite.**
`fixture-builder-v2.py` sets `revision = git(root,'rev-parse','HEAD')` (2nd commit) and the oracle
always passes `--rev f['rev']` = HEAD. Therefore `input_revision == f['rev']` holds for a tool that
(a) echoes the literal `--rev` argument, (b) reports repo HEAD regardless of `--rev`, or (c) reports a
constant 40-hex string, and (f) reports any *other* HEAD-like OID is excluded only by accident.
No r23 arm varies `--rev` away from HEAD, so no requirement can distinguish (a)/(b)/(c).
r22's `AttackR24.md` proposed exactly this arm (**F24-A**: `--rev HEAD`, then `--rev <12-hex prefix>`,
expecting `input_revision` to be the *resolved* full OID ≠ the literal argument). It is **not** in the
frozen requirement set, and the r23 driver explicitly declines to adapt historical r22 batteries
(`measure-round23-v2.py:1173-1175`: "the r23 oracle re-expresses the predicates and no historical r22
mutant battery is adapted here").

**CE-2 — `inputs_sha256` cannot distinguish Git-blob reads from worktree reads.**
The tool reads committed blobs (`:167`), but the oracle's expectations are the builder's worktree
digests, which coincide with the blobs only because the builder commits those bytes. Replacing
`:167` with a worktree read (`(repo/p).read_bytes()`) keeps `inputs_sha256` identical on every arm —
including the `policy-changed` / `allowlist-changed` arms, where the builder *also* commits the
changed bytes. r22's **F24-B** (post-commit worktree divergence) is the arm that would separate them;
it is absent.

**CE-3 — `argv` may be empty.**
The predicate is `isinstance(v['argv'],list)`; `'argv':[]` passes. The r23 oracle never compares the
emitted argv with the command it ran. r22's stronger refinement arm does
(`refinement-reconcile.py:200`: `obj.get('argv')==cmd[2:]`) and also pins the exit-2 key set to
exactly `{schema, finding_id, error, privacy_clearance, receipt_match}` — neither is run by r23.

**CE-4 — `measured_revision` is echo-consistent.**
Both sides read the *same* field (`wrapper['measured_revision']`); the tool's independent checks
(`:171-175`: OID form, `rev-parse` peel equality, `merge-base --is-ancestor`) are never *challenged*
by an arm, so R24 cannot show that the measured revision is bound to the scanned tree rather than
merely copied. r22's **F24-C** (inner `commit` split) and **F24-D** (annotated-tag OID) would.

**CE-5 — `tool_sha256` is self-attesting.**
The tool digests the file it is executing (`:240`); the oracle digests the file it handed over. Any
implementation — including a wholly different one — satisfies this conjunct. It can fail only if the
file changes between the run and the comparison. It binds nothing to the *committed* blob; that
binding is supplied by the driver's staged-tool digest and by the source-delta guard (§3.1), which is
where the real evidence lives.

**Net:** the five counterexamples do not change R24's pass/fail status; they bound what a green R24
licenses anyone to say. R24 certifies "the tool's self-report is internally consistent with the
fixture the oracle built" — it does not certify that the tool *resolved*, *bound*, or *read* what it
reports.

## 6. Where the C1 no-harm claim actually rests (and where it is thinner than it looks)

The contract clause "**No other output key, value, exit code or finding id changes**" is **not**
witnessed by any frozen requirement:

* R25 checks only that the literal key `raw_unallowlisted` is absent from the **top level** of each
  parsed run (`oracle-rename.py:82`). A renamed alias (`raw_unallowlisted_v1`, `legacy_unallowlisted`)
  passes R25; a nested alias would also pass (top-level membership test only).
* No requirement pins the output **key set**. A tool that additionally dropped
  `receipt_authenticity:'unattested'` (the honesty marker) would still be 26/26.
* Key-set comparison of before vs after outputs from the committed evidence (`measure4/c1-{before,after}-observed.json`)
  confirms that in practice exactly one key disappeared and none was added:

| arm | before keys | after keys |
|---|---|---|
| `valid` / `drop` / `forbidden` (check output, 25 → 24 keys) | 25 keys incl. `raw_unallowlisted` | 24 keys, identical set minus `raw_unallowlisted` |
| `malformed` (setup error, 5 keys) | `{error, finding_id, privacy_clearance, receipt_match, schema}` | identical set (only the `schema` *value* changes v1→v2) |

That is **evidence**, but it is evidence about *this* implementation, not a frozen requirement.

**What actually closes the gap** is the byte-level source-delta guard (§3.1, enforced by `C21`/`C22`):
because `final = entering` with exactly two textual edits, no *other* output key, value, exit code or
finding id can have changed, and no alias can have been introduced. My independent byte comparison
reproduces that proof from the two git blobs. The r23 requirement set alone would not have established
it — **the requirement set is weaker than the claim it is attached to; the guard is what makes the
claim true.** (Corroborated by wave-1 seats `build/CriticRenameHarm.md` §F3/F4 and
`build/ReviewOracleRename.md` §W1/G2 — same shape, same files; not claimed as novel.)

**The one place where the byte proof is *not* a substitute:** the r22 refinement suite (19/19) carried
a **strictly stronger provenance envelope** than R24 — `refinement-reconcile.py:199-200`:
`inputs_sha256` recomputed by the runner from `git show rev:path`, `argv == cmd[2:]` exactly,
`input_revision == rev`, `measured_revision == wrapper['measured_revision']`, plus the exit-2 minimal
key-set assertion at `:202`. It is not run by the r23 driver, and it cannot be carried over unchanged

## 7. Residual risk and verification gaps (bounded)

1. **R24's green is not admissible as a C1 no-harm witness.** Anyone citing "R24 pass" as evidence
   that C1 preserved the reconciler's provenance behaviour is over-reading: CE-1…CE-5 show five
   implementations that pass R24 and would not preserve it. Cite instead: the source-delta byte
   proof (`c1-source-delta.json` + `C21`/`C22`) and the real control.
2. **The r22 kill matrix is not carried.** The contract declares "Before→after for C1 is measured by
   the r23 oracle only"; the driver repeats it (`:1173-1175`). Consequently r22's 22-mutant battery
   (of which, per r22's own evidence, 14 mutants turned **no** frozen row red) is not re-run against
   the post-C1 tool. The C1 *delta* is still safe (byte proof), but any pre-existing weakness the
   matrix would have exposed (M1…M7 of `AttackR24.md`) remains unexposed and is inherited, not
   introduced. This is a depth/rigor gap, not a C1 regression.
3. **R24 covers the exit-0 arm only.** The exit-1 arms (R05–R10) are checked for exit code and
   `finding_id` only; no requirement asserts that a mismatch output carries `receipt_match=false`,
   `differences`, or any provenance field. r22's F24-G proposed exactly that.
4. **Exit-2 output minimality is unasserted in r23.** The r22 suite asserted
   `set(obj)=={schema,finding_id,error,privacy_clearance,receipt_match}` on every exit-2 arm; the r23
   oracle asserts only `finding_id` + exit code. The shipped tool does emit exactly that 5-key set
   (verified from `measure4` `malformed`/`symlink`/`invalid-revision` arms) — verified here, but not
   frozen.
5. **`--rev` resolution semantics are untested.** CE-1 means "the reported `input_revision` is the
   single `^{commit}` peel of `--rev`" is an *undocumented, unenforced* behaviour of the shipped tool
   (the tool does implement it at `:165`/`:67-70`), not a property R24 establishes.
6. **Not my scope, recorded for the L1 only:** `measure4/summary.json` shows
   `all_claim_checks_pass=false` and `real_controls_pass=false`, caused by exactly two failing driver
   checks — `C34.c2_after_every_case_matches` (29/30) and `C30.c2_oracle_real_control_agrees` — both
   on the **C2** quota axis (the frozen `CaseEscapedSpace` contradiction). Every C1 check passes
   (`c1_original_26.pass=true`). No C1 defect was found; the strict red is C2's and is expected per
   the round-23 disposition. Nothing in this report reclassifies, re-labels, or works around that case.

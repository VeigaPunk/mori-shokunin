## 6. Falsification attempts (each closed with a concrete reason)

1. **"R19 might pass vacuously"** (setup error raised by something unrelated to duplication). *Rejected:* the recorded stdout for the `duplicate` arm carries the **specific** token `duplicate_receipt_hit`, in both arms. Static trace of `check()` shows every earlier check passes for this fixture (receipt schema, measured-revision peel + `--is-ancestor`, policy/allowlist committed bytes unchanged at the measured revision, policy/allowlist shapes, `exit_code∈(0,1)`, `stderr==''`, argv `--repo/--policy/--allowlist/--rev` bindings, `commit`/`policy_sha256` binding, integer counters) and the first failing check is `normalize_hits` on the receipt's claimed `hits` (line: `key=hit_key(hit); require(key not in seen,'duplicate_receipt_hit')`), reached through the dict comprehension over `('hits','unallowlisted_hits','allowlisted_hits')` — `hits` first.
2. **"The fixture could have been co-evolved to make R19 trivial."** *Rejected:* the `duplicate` arm is a single `deepcopy` append to the receipt's claimed hits, taken from the unchanged r22 builder whose bytes are identical at the r22 freeze, at the r23 seal and in the working tree; the driver runs the seal-staged builder and the pinned builder hash.
3. **"The C1 edit could have broken R19."** *Rejected:* the two transformations provably cannot affect exit code, `finding_id` or stderr on the `Invalid` path (§3), and R19's predicate reads only those three plus JSON-parseability.
4. **"R19 could be shadowed or re-indexed by the R25 insertion."** *Rejected:* results are keyed by explicit `id` strings; `results.insert(24, …)` inserts the R25 row between R24 and R26 and cannot alter R19's recorded row or its variant; the measured row for R19 is bound to variant `duplicate`.
5. **"A tool without duplicate rejection would still satisfy R19"** (would make R19 non-discriminating). *Rejected by static reasoning over `check()`* [`INFERENCE`, no execution]: with the duplicate present in the claimed hits but not in the scanned tree, `claimed['hits'] != Counter(hit_key(h) for h in actual)` → `differences` non-empty → finding `RETENTION_RECONCILIATION_MISMATCH`, exit **1**, not exit 2/`SETUP`. R19 therefore separates "duplicate rejected" from "generic mismatch", and also separates them from the *mismatch* family (R05–R10 expect exit 1).
6. **"R19 might have been satisfied only after the change"** (i.e. a newly-introduced green). *Rejected:* R19 passes in the **before** arm too (25/26 with only R25 unmet), so it is a pre-existing semantic guarantee carried through the cutover, not a product of it.
7. **"The before/after arms could have used different fixtures"** (inflating the before/after comparison). *Rejected for R19 specifically:* the `duplicate` fixture is generated deterministically from the same sealed builder; the recorded before/after `duplicate` stdout differ **only** in the `schema` string, and the R19 predicate does not read `schema`.

## 7. R25 (API cutover) vs R19 (unchanged semantic requirement)

* **R25** is the API-cutover requirement (`oracle-rename.py:78`): every parsed oracle run must have `schema == "mori-retention-reconciliation-v2"` **and** no key `raw_unallowlisted`; it is the only unmet requirement before the change (before: 8 alias-carrying runs; after: 0).
* The 8 alias-carrying runs before the cutover are exactly the success-path outputs: `valid, drop, inject, digest, line, class, metric, forbidden`. The `duplicate` (R19) run is a **setup** output and never carried the alias — so "alias 8 → 0" cannot be attributed to anything touching R19's arm; the alias lived only in the success-path dict whose key was deleted.
* **R19** belongs to the other family: unchanged semantic requirements (duplicate rejection, malformed receipt, symlink receipt, unsafe path, revision binding, …) that the cutover neither relabels nor relaxes. The r22→r23 oracle diff confirms R19 was neither renamed nor re-expressed; the only semantic arm rewrites were R02/R11/R12 (field substitution only, same expected values 1/3/1).
* The r23 driver keeps the two families in separate check buckets (`ORIGINAL_26_CHECKS` vs `SUPPLEMENTARY_CHECKS`, lines 110–116), so the byte guard (`C21`/`C22`) and the same-instance replay (`C23`) never redefine the original-26 denominator that contains R19.

## 8. Residual risks and verification gaps

1. **Predicate under-specification (low, measurement gap).** R19 asserts exit 2 + `finding_id` + empty stderr but not the error token. A future change that made the duplicate fixture fail for a *different* setup reason (e.g. `receipt_hit`, `policy_changed`, `receipt_argv_binding`) would still satisfy R19 while silently ceasing to test duplicate rejection. Today's tool is correct (recorded token `duplicate_receipt_hit`), but the requirement would not catch that regression. A supplementary, separately-labelled assertion on `error == "duplicate_receipt_hit"` would close it; the frozen original26 must not be rewritten.
2. **Coverage of the duplicate path is single-armed.** Only the receipt-side duplicate is exercised. The tree-side `normalize_hits(hits)` inside `scan()` cannot trigger on a Git tree (hits are derived one-per-(blob,line,class)), so no unreachable-branch claim is being made; but a duplicate arriving via a *different* receipt field (`allowlisted_hits`, `unallowlisted_hits`) is not separately armed — the same `normalize_hits` would reject it, which is reasoned statically, not measured.
3. **Evidence is from committed receipts, not from my own execution.** My scope was static; I did not run the tool, the oracle or the driver, and I performed no live host reads. The before/after R19 rows cited are the committed `evidence/measure4/` artifacts produced at the pinned revision `f3dc07c0` (independently mirrored under `falsify/RerunPinnedDriver/`).
4. **Interpreter/environment drift between arms is excluded but not formally pinned.** Both arms ran inside one driver process, so the interpreter is identical across before/after; a *future* re-run on a different interpreter is not covered by any frozen pin I found.
5. **Scope of the byte guard.** It constrains exactly one file (`tools/mori-retention-reconcile.py`) at one revision pair. R19's outcome also depends on the Python runtime and on `git` behaviour; a runtime change could alter `json`/`Counter` semantics, but nothing in the frozen artifacts pins the interpreter version.

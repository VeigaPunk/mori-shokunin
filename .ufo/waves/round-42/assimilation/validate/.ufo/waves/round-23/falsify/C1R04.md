## 2. The exact frozen predicate


`policy_excluded_hits`) must equal the fixture builder's independently computed expectations

## 6. Is R04 discriminating, or vacuous? (the core falsification attempt)

it compares the tool's independent re-scan against the *fixture builder's* independent
expectation. I extracted the r22 mutant corpus (22 mutants, `measure-round22.py:84-108`,

## 8. Findings, by severity

**No blocking finding.** No counterexample to R04 exists in the frozen bytes.

### MEDIUM — R04 covers one arm only; `must_redact_paths` semantics are outside R04
R04 is recorded on the `valid` fixture arm only. Mutations that break the
must-redact / forbidden-allowlist path leave R04 green (empirically: `aux-unchecked` and
`forbidden-not-red` are R04-green and are caught only by the r22 refinement layer; R11
carries the forbidden arm in the r23 oracle). This is a **coverage boundary, not a defect**,
but it must not be reported as "R04 validates exclusion semantics" — R04 validates the
*non-author glob* exclusion on one arm; the forbidden/`must_redact_paths` exclusion is R11's
and the refinement cases'.

### MEDIUM — both sides of R04 are authored by one builder (co-evolution surface)
The receipt and the expectation lists come from the same `fixture-builder-v2.py`. R04 is
therefore *tool-vs-builder*, not *tool-vs-external-truth*: a co-evolved builder error is
invisible to R04 by construction. Concrete coupling found in the fixture source:

* `fixture-builder-v2.py` computes `hits` over `files` **before** `files[ALLOW]` is added
  (`files[ALLOW]=encoded({'rows':rows})` happens after the hit loop), so the builder never
  scans `allowlist.json`, while the tool **does** scan it (it is committed in the measured
  tree). The two agree only because `allowlist.json` contains no policy-regex-matching
  line. A fixture whose allowlist matched the policy regex would make the tool report 6 raw
  hits against the builder's 5 — a **false red** in R04 (and R03/R22), not a tool defect.
  Current frozen fixture: no matching line, so no effect today.

### LOW — order-sensitivity of the excluded clause is vacuous at n=1
`v['policy_excluded_hits']==f['expected_policy_hits']` is order-sensitive, but the frozen
fixture's excluded set has exactly one element (`non-author.txt:1`). A regression that
reorders (or duplicates within order) the exclusion output would still pass R04. Mitigation
exists elsewhere (the tool emits `hits`/`scanner_hits`/`policy_excluded_hits` from a single
ordered list and `normalize_hits` rejects duplicates; setup error path covered by R19), so
this is a narrow gap, not an open hole.

### LOW — exclusion-mechanism coupling between builder and tool
The builder hard-codes the excluded path as the literal `'non-author.txt'`
(`expected_policy_hits=[h for h in hits if h['path']=='non-author.txt']`), whereas the tool
derives exclusion from the policy's `non_author_paths_glob` via `fnmatch`
(`is_non_author=lambda h:any(fnmatch.fnmatch(h['path'],pattern) …)`). They coincide only
because the fixture's glob is that exact literal. A glob-valued fixture (e.g.
`non-author.*`) would make the builder's expectation wrong while the tool is right — again
a false-red surface, not a tool defect, and it does not apply to the frozen bytes.

### LOW — guard strength boundary (already acknowledged in the amendment)
`c1-source-delta.json` states its own scope: "byte-exact source constraint … not arbitrary
semantic equivalence". My recomputation confirms the constraint holds for the pinned
production source, but it certifies R04 only relative to the entering revision, whose own
correctness rests on r22's separate measurement. R04 is *not* re-proved as ground truth
about retention semantics; it is re-proved as an unchanged, discriminating requirement.

### INFORMATIONAL — non-blocking observations
* `scan()` caches parsed blobs by object id while keeping `path` in every hit identity; the
  cache is per-path-safe (path is re-attached on `hits.extend`), so R04's set equality is
  not at risk from the optimization.
* R04's dict equality is exact on hit fields (`path`,`line`,`class`,`line_sha256`): a tool
  that added a field would fail R04 — conservative in the safe direction.
* `sorted()` by `(path,line)` makes R04 order-insensitive for `scanner_hits` (intended)
  while `policy_excluded_hits` stays order-sensitive (asymmetric by design; see LOW above).

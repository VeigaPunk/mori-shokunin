## 9. Findings by severity

### F-1 — LOW / INFORMATIONAL (R22 is logically dominated by R01/R03/R04; redundancy, not falsity)

R22's *unique* content over the rest of the 26 is its second clause (binary exclusion); its first
clause (`raw_total==5`) is already asserted by R03 (`(raw_total,policy_excluded,scanner_total)==(5,1,4)`).
Tracing the mutant space over the frozen fixture:

- Deleting the NUL skip (`tools/mori-retention-reconcile.py:150`) → `binary.bin` yields one extra hit
  (`R22_SAMPLE\x00must-not-count`, line 1, class `R22`) ⇒ `raw_total=6` ⇒ **R22 fails** (both clauses).
  But the same edit also makes the tool's hit set disagree with the frozen receipt ⇒ `differences=['hits',…]`
  ⇒ `finding_id=RETENTION_RECONCILIATION_MISMATCH`, `exit=1` ⇒ **R01 fails too**, and R03/R04 fail as well.
- Substituting `binary.bin` for another path while keeping `raw_total=5` ⇒ R22 fails, but R04 (set
  equality of `scanner_hits` against the fixture's `expected_scanner_hits`) fails as well.

So under this frozen fixture **no mutant exists in which R22 is the only failing requirement**: R22's
binary clause adds no *independent* detection power beyond R01/R03/R04. It is nonetheless a correct,
non-vacuous restatement, and it is the *only* requirement that names the binary exclusion explicitly.
Assessment: redundancy (not vacuity) — the predicate is genuinely evaluated over a population that
contains `binary.bin` (§4). No change requested; noted so the denominator is not read as 26
independent detections of 26 distinct properties.

### F-2 — INFORMATIONAL (R22 pins the tool's *actual* binary criterion, not "binary" in general)

The tool's only binary test is `b'\0' not in raw` (line 150); blobs that are invalid UTF-8 **without** a
NUL byte are still scanned, because decoding uses `errors='replace'`. R22 therefore pins
"NUL-containing blobs are skipped" and says nothing about other binary shapes. This is **inherited
r22 behaviour** (the scan path is byte-identical to `1bfe708`), not introduced by C1, and it is not
something the C1 cutover may repair. The four unallowlisted inherited retention hits and the other
carried debt remain open, unchanged by this finding.

### F-3 — INFORMATIONAL (the two oracle arms are not the same fixture *instance*)

`oracle-rename.py` builds a fresh fixture per arm, so the before-arm ran on `…/c1/before-fixtures/valid`
(`rev=18e2af21b596e2ce225221a621deafd09704d2b0`) and the after-arm on `…/c1/after-fixtures/valid`
(`rev=afa221f99550ed73a68c132e9d61b796150629eb`). The `rev` differs because the fixture's retained
receipt embeds its own absolute repo path in `argv`, so the second commit hashes differently; the
**`measured_revision` is identical (`a8e8b5dfb9cc19c66ae3d13f16bee3fa86b36a34`)**, i.e. the scanned tree
is byte-identical on both sides. The amendment's `same_fixture_required` is discharged separately and
correctly by the driver's replay (check `C23`), which runs *both* tools on the **after** fixture
instance and compares outputs key-by-key (`differences: []`). Impact on R22: **nil** — R22 depends only
on the scanned tree and the tool bytes, both identical across arms. Recorded for completeness so the
"before 25/26 vs after 26/26" comparison is not misread as a same-instance A/B (it is a
same-population A/B; the same-instance A/B is C23).

R22's predicate is byte-identical to r22's, its fixture population is present and pinned by digest,

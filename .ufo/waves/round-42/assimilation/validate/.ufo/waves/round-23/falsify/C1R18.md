### Axis 2 — Discriminating power: **FALSIFIED (two concrete counterexamples)**

R18's green is *true in fact* (the shipped tool does reject both bools with the right internal
reasons — `receipt_hit_type` / `receipt_counter_type`, visible in the retained run stdout), but the
**frozen predicate** cannot demonstrate that. Two concrete counterexamples:

**CE-1 — reason-agnostic row (any setup failure satisfies R18).**
`record()` binds only exit code, `finding_id` and empty stderr; the bool-metric conjunct binds
even less (no stderr, no `error`). Therefore a tool that fails the bool-line fixture for an
*unrelated* reason — e.g. raising `Invalid('receipt_argv_binding')`, `Invalid('receipt_revision')`
or `Invalid('input_unavailable')` before any type validation — satisfies **both** R18 conjuncts and
R18 goes green. The retained evidence shows the shipped tool takes the intended branch
(`error=receipt_hit_type`, `error=receipt_counter_type`), but the row cannot attest that: the
error token is exactly the field that distinguishes the intended branch from an incidental one,
and it is not in the predicate. (Same defect, unchanged, already recorded for r22 in
`round-22/falsify/FinalR18.md` §"The row is reason-agnostic".)

**CE-2 — non-colliding arm ⇒ a false-green mutant passes R18 (concrete).**
Because `hits[0]` is `policy.json` line **13**, the bool-line arm never tests the only value where
a boolean can pass an equality comparison (`True == 1`). Consider mutant **M2′**: keep the counter
guard strict (as in the real tool) but perform the `line` type check only when a comparison
difference already exists — concretely, drop `integer(hit['line'])` from `normalize_hits()` and
add `if any(not integer(k[1]) for k in claimed[field])` inside the *differences* branch of the
comparison loop. Static evaluation of M2′ against the frozen fixture:

- bool-line arm: comparison finds a difference (scanned `13` vs receipt `True`, and
  `13 != True`), differences non-empty → strict line-type check fires → `Invalid` → exit 2,
  `error=receipt_hit_type` → **R18 conjunct 1 satisfied**;
- bool-metric arm: counter guard still strict → exit 2, `error=receipt_counter_type` →
  **R18 conjunct 2 satisfied**;
- ⇒ **R18 is green under M2′.**

But M2′ admits a **false green** that the shipped tool forbids: a receipt whose
`unallowed.txt` line-1 hit carries `"line": true` in *both* `hits` and `unallowlisted_hits`.
`hit_key` is `(path,line,class,line_sha256)` and `Counter` equality compares dict keys, and
`('unallowed.txt', True, 'R22', sha) == ('unallowed.txt', 1, 'R22', sha)` because `True == 1`; so
no difference is detected, no type check runs, and the tool returns **exit 0,
`RETENTION_RECONCILED`, `receipt_match: true`** for a receipt carrying a JSON boolean in a
position the schema declares an integer. The shipped tool rejects this
(`normalize_hits` → `receipt_hit_type`, exit 2), so this is a defect of the *evidence*, not of the
shipped tool: **R18 does not discriminate M2′**, and the frozen fixture cannot reach the collision
case because the fixture's bool arm targets line 13, not line 1.
(Recorded for r22 in `round-22/falsify/FinalR18.md` §C1 and `round-22/falsify/FixtureBoolLine.md`;
the r23 re-expression preserves the arm byte-for-byte, so the defect is carried into r23 unchanged.)

**Consequence for the C1 claim:** C1 does not create this defect and does not worsen it. But
R18's after-green must not be cited as evidence that C1 "preserved bool rejection" beyond what
Axis 1 proves (source-byte identity) — the row adds no independent information.

### Axis 4 — Guard coverage: **AGREE (complete for R18)**

The guard's own honesty caveat (source constraint, not semantic proof) does not weaken the R18

### Axis 5 — Attribution: **R18 is NOT a cutover measurement**

R18 is an *unchanged semantic requirement*: its predicate text, its fixture bytes and its

value-preserving (1/3/1 unchanged) and no semantic requirement is weakened; the independent

## 8. Residual risk

1. **R18 as evidence is weak.** A future edit that replaced the unconditional `integer()` check
   with a mismatch-conditional one (M2′) would keep R18 green while admitting a bool at line 1 as
   a reconciled receipt. The byte-exact guard would *not* catch it if it landed in a later round
   (the guard is scoped to *this* cutover's exact byte delta, by design).
2. **The false-green shape is not exercised anywhere in the frozen suite.** No frozen arm mutates a
   line value to `True` at a line number where `True == 1` (i.e. line 1 of a scanner hit), so no
   requirement row in r23 would detect the collision.
3. **Reason-agnostic rows generally.** Every `record(..., code=2, 'RETENTION_RECONCILIATION_SETUP')`
   row (R13–R21) shares the same under-determination; R18 is the one I was assigned.
4. **No red-control suite in r23.** The whole original-26 denominator is currently green-without-
   fail-capability evidence for at least R18; a driver-level semantic mutation set (r22-style)
   would restore the calibration that r22 had and r23 dropped.

## A3 — discriminating power of R11 (concrete counterexamples)

Rejected by R11 (each fails at the pinned semantics):

| # | wrong implementation | why R11 catches it |
|---|---|---|
| M1 | in-scope count computed over **raw** hits instead of scanner hits | forbidden arm yields 4 ≠ 3 → predicate false |
| M2 | must-redact rows treated as *allowlisting* | `allowed.txt` hits re-enter `allowed_keys` → 1 ≠ 3 |
| M3 | forbidden allowlist rows not detected | `forbidden_allowlist == 0` → predicate false |
| M4 | receipt reconciliation broken (mismatch) | `finding_id` becomes `RETENTION_RECONCILIATION_MISMATCH` → `record()`'s finding check fails |
| M5 | unparsable / non-JSON stdout on the forbidden arm | `isinstance(v, dict)` false → `ok` false (fails closed) |

**Not** caught by R11 alone (bounded residuals):

* **R-1 — type laxness in the numeric conjuncts.** `v['forbidden_allowlist']==1` and
  `v['scanner_unallowlisted']==3` are Python `==`, so a producer emitting `forbidden_allowlist: true` or
  `scanner_unallowlisted: 3.0` **passes R11** while violating the integer-counter contract.
  `retention_state=='red'` (string) and `privacy_clearance is False` (identity) are strict; only the two
  counters are lax. r22's build analysis explicitly required strict typing for exactly these counters
  (`.ufo/waves/round-22/build/AttackR18.md`: "must themselves be `type is int` … the oracle checks types,
  not just `==`"). The r23 re-expression carries the *value* expectations forward but not the *type*
  expectation. At the pinned revision this is neutralised by two independent facts — the producer is
  `len(...)` (always `int`) and the byte guard (A4) forbids any edit of that line — but R11 as a
  behavioural requirement does not itself carry the type contract.
* **R-2 — no alias-vs-canonical cross-check survives.** Pre-cutover, R02 was the only requirement that
  compared the alias with the canonical counter (`raw_unallowlisted==1 and scanner_unallowlisted==1`);
  after the mechanical substitution it reads `v['scanner_unallowlisted']==1 and v['scanner_unallowlisted']==1`
  — a literal self-duplicate. The alias's value is therefore no longer cross-checked anywhere in the 26;
  R25 pins only *absence*, and the anchor for the alias's historical value (4 on the real receipt) now
  lives solely in the real control's `scanner_unallowlisted: 4`. R11 itself never compared the two keys,
  so R11's coverage is intact — but the substitution's mechanical nature is visible in R02.

## Findings by severity

**F1 — WITHDRAWN AS A DEFECT (corrected in the addendum below; retained here for traceability) — original
claim: `policy_excluded` is a surviving misleading field name of exactly the class C1 removed.**
`tools/mori-retention-reconcile.py` computes `excluded` by `non_author_paths_glob` matching and reports it as
`'policy_excluded': len(excluded)` with the self-declared `'exclusion_basis': 'non_author_paths_glob'`.
The newly frozen C1 real control (`frozen/c1-expected-real.json`) cements `policy_excluded: 5` /
`scanner_total: 90` (= 95 − 5) / `non_author: 5`. I originally contrasted this with the "policy-source-file
exclusion = 4 / scanner_total 91" figures appearing in round-22 **build-seat proposal notes**
(`.ufo/waves/round-22/build/RawPartition.md`, `ReportContract.md`) and called the surviving name a
misnomer. The L1 adjudicated that reading as rejected in r22 (formal frozen policy defines exclusion by
`non_author_paths_glob`; `policy_excluded` means policy-selected exclusions = 5, not policy-source-file
exclusion = 4). The r22 **frozen accepted** real control
(`.ufo/waves/round-22/frozen/expected-real.json`) already records `policy_excluded: 5`, `scanner_total: 90`,
`exclusion_basis: "non_author_paths_glob"` — so the C1 real control is a faithful carry-forward of the
accepted r22 semantics. **F1 is therefore withdrawn as a formal SUT/count defect** and downgraded to an
informational reader-terminology note only; no rename, no frozen-semantics change, no new field.
See “Addendum — L1 adjudication on F1” at the end of this report.

**F2 — Low (inherited oracle laxness, not a C1 regression) — R11's counter conjuncts are type-lax (R-1 above).**
Concrete counterexample: a producer
emitting `forbidden_allowlist: true` and `scanner_unallowlisted: 3.0` satisfies R11 verbatim
(`True == 1`, `3.0 == 3`) while breaking the integer-counter contract that r22's **build-seat** attack
analysis required (`.ufo/waves/round-22/build/AttackR18.md`: "must themselves be `type is int` … the oracle
checks types, not just `==`"). The **accepted frozen** r22 oracle itself uses `==`
(`oracle-reconcile-v2.py:52`), so the type expectation was never enforced by the frozen requirement set;
the r23 re-expression is faithful to it. Fixing it would mean
`type(v['scanner_unallowlisted']) is int and v['scanner_unallowlisted']==3` (and the same for
`forbidden_allowlist`) in R11/R02/R12. Today the byte guard plus `len()` make it inert,
but a future revision that re-opens the file could regress the types without turning any of the 26 red.

**F3 — Low — the alias↔canonical cross-check collapsed into a tautology (R-2 above).** R02's two conjuncts
are now literally the same comparison. Post-cutover nothing in the original 26 compares the removed alias's
value with the canonical counter; the only remaining anchor for the alias's historical value (4) is the real
control's `scanner_unallowlisted: 4` plus `raw_not_allowlisted: 9`. Low severity because the byte guard and
the real control jointly pin the value, but it should be recorded so the 26/26 is not read as "26 independent
checks".

**F4 — Low — the source guard tolerates a missing frozen artefact.** `guard_ok = bool(guard_ok and delta_ok is not False)`
(`measure-round23-v2.py:686`): if `frozen/c1-source-delta.json` were unreadable, `delta_ok` stays `None` and
C21 still passes. No live gap — the artefact is sealed at `22772c1…`, staged from the seal and digest-pinned
by C05/C11 — but the check is fail-open in that one dimension.

**F5 — Info — R11's `3` is single-authored.** The oracle literal `3` and the builder's
`'expected_raw_unallowlisted': 3 if forbidden else 1` come from the same L1-authored fixture lineage and
are not independently derived; the count additionally depends on the fixture's dedup property (two

R11's independence, matching r22's own K4 note that the two counters are "one observable stated twice".

The C1 real control is therefore a faithful carry-forward of the **accepted r22** semantics, and the

**What remains of F1 (informational only, no action):** a reader who recalls the superseded r22 contract

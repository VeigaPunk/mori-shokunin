## 3. Concrete counterexample — R20 does not test what it names

**Mutant M1 (single-token change, no other byte touched).** In
`tools/mori-retention-reconcile.py:51-52`, `safe_path` currently rejects any path
component in `{'', '.', '..'}`:

```python
def safe_path(path):
    require(isinstance(path,str) and path and not path.startswith('/') and all(p not in ('','..','.') for p in path.split('/')) and not any(ord(c)<32 or ord(c)==127 for c in path),'unsafe_input_path')
```

M1 deletes only the `'..'` element of that set, i.e. the lexical traversal guard is gone.

**Trace of M1 on the R20 arm:**

1. `check()` (line 166) `paths={'receipt':safe_path(a.receipt),…}` — `'../receipt.json'`
   now passes the lexical gate.
2. `committed(repo,revision,'../receipt.json')` (line 87) → `tree()` (line 73) →
   `git --no-replace-objects -C repo ls-tree -r -z --full-tree <rev> -- ../receipt.json`.
3. **Observed git behaviour (read-only probe, git 2.56.0, lane repo, no writes):**

   ```
   $ git --no-replace-objects -C <lane> ls-tree -r -z --full-tree HEAD -- ../contract.md
   fatal: ../contract.md: '../contract.md' is outside repository at '/home/vgpnk/Projects/shokunin/mori-shokunin'
   exit=128
   $ GIT_LITERAL_PATHSPECS=1 git … -- ../contract.md        # identical
   exit=128
   ```

   The tool's `git()` wrapper (line 55–61) then raises `Invalid('git_read_failed')`.
4. `main()` (line 287) catches `Invalid` and emits the *same* observable envelope:
   `{"error":"git_read_failed","finding_id":"RETENTION_RECONCILIATION_SETUP",
   "privacy_clearance":false,"receipt_match":false,"schema":"mori-retention-reconciliation-v2"}`,
   exit 2, stderr empty.

**R20 on M1:** exit 2 ✔, JSON object with `finding_id == RETENTION_RECONCILIATION_SETUP` ✔,
stderr empty ✔ → **R20 PASSES**.

**Robustness of the counterexample.** The outcome does not depend on git refusing the
pathspec: if a git version instead returned zero rows, `committed()`'s
`require(len(rows)==1 and rows[0][3]==path,'missing_input_blob')` (line 88) raises
`Invalid('missing_input_blob')` — same envelope, same exit 2, same empty stderr (a tree
cannot contain a `..` component, so zero rows is the only other possible outcome). Either
branch satisfies R20. R20 therefore cannot distinguish *"rejected because the path is
lexically unsafe"* from *"rejected because git refused it"* or *"rejected because the blob
is absent"* — the three are indistinguishable to the frozen predicate.

**M1 leaves the whole 26 green.** R01/R03/R04/R22/R23/R24/R26 use the safe `valid` arm
(unchanged); R05–R12 use data-mutation variants of the safe arm; R13–R19 are semantic
setup errors; R21 is the symlink variant, rejected by the `mode in (100644,100755)` check
in `committed()` (line 90), not by `safe_path`; R25 stays green because M1 keeps
`SCHEMA='…-v2'` and the setup envelope never carried `raw_unallowlisted`. Net: **M1 would
still measure 26/26 with `misleading_alias_runs = 0`.**

**Therefore:** R20 provides *zero* evidence for the traversal rejection it is named after.
It is satisfied by "some exit-2 setup envelope", including one produced by an
implementation with no lexical dotdot guard at all.

1. **R20 is blind to the very field C1 changed.** A tool that kept `SCHEMA='…-v1'` in the

   reads `schema`); only R25 turns red. Conversely, the "no `raw_unallowlisted`" half of

2. **R20's arm is one of the 18 runs R25 counts.** The R20 setup envelope is one of the
   parsed objects in `parsed_runs`, so the C1 schema change is visible in R25 *through*
   R20's arm, but only via R25.

## 5. Residual risk and verification gaps (in scope)

1. **R20 is a false-green generator for path-safety regressions.** Any future round that
   relaxes the byte-exact source guard, or that re-ports the C1 predicate textually without
   re-adding cause-level arms, will report R20 green while the traversal guard is absent.
   Mitigation available without touching the frozen oracle: re-express the r22 refinement
   arms (`unsafe-receipt`, `unsafe-policy`, `unsafe-allowlist`, `control-path`) as a
   *separately labelled* supplementary guard that asserts the frozen error token
   `unsafe_input_path` and a minimal stdout key set, reported apart from the original 26
   denominator (the same separation the round already uses for the 5 supplementary guards).
2. **Unarmed path classes in the r23 26:** only leading `..` on `--receipt` is exercised.
   Absolute paths, empty strings, control bytes, interior `a/../b`, `.` components, and the
   same classes on `--policy`/`--allowlist` are unarmed. Note the asymmetry measured in
   §3: git normalises a `.` component silently (`ls-tree … -- ./tools` returned rows named
   `tools/…` in the read-only probe), so the `.` class is *not* fail-closed by git and the
   tool's lexical rule is the only barrier for it.
3. **Setup-envelope minimality is not asserted anywhere in the r23 measurement.** The
   replay guard's `differences: []` means "before == after apart from schema /
   `raw_unallowlisted` / `tool_sha256` / argv" — it is an *equality* guard, not a
   *minimality* guard. An implementation that echoed `argv` (and hence the attacker-chosen
   `../receipt.json` bytes) into the setup envelope would still satisfy R20 and the replay.
4. **Ordering assumption (A4 in the r22 attack note) is observable but unfrozen:** the tool
   resolves the revision before validating the path, so an arm combining a bad `--rev` with
   an unsafe path reports `invalid_revision`, not `unsafe_input_path`. R20 uses a valid
   `--rev`, so the ordering is invisible to it.
5. **The counterexample's git branch is version-bound.** The "outside repository" refusal
   was observed on git 2.56.0 only; the zero-row branch (which yields the same exit-2
   envelope) is the fallback and does not depend on the git version.

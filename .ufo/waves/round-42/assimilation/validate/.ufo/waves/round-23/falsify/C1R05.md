## 1. Verdict

**R05 is not falsified by the C1 cutover — bounded agree.** R05's frozen predicate is
byte-identical between the r22 and r23 oracles, is exercised by the pinned schema-v2 tool, and
holds under the byte-exact source-delta guard with the same exit code, finding id, difference
set and recomputed counters before and after. R05 is one of the **25 unchanged semantic
requirements**; the *only* requirement whose status moves is **R25** (before `False` → after
`True`), which is the API-cutover requirement.

The bound is real and I state it plainly: **R05 in isolation is a weaker discriminator than the
capability it stands for** (concrete counterexample in §5, F1). It proves *that a receipt whose
raw hit list lost an identity is rejected with exit 1 / MISMATCH*; it does **not** by itself
prove the tool re-derived the population from the committed tree. That proof is supplied
jointly by R03/R04 (which pin `raw_total`/`policy_excluded`/`scanner_total` and the exact
`scanner_hits` identity list), and by the byte-level guard in §4. This is inherited from the
frozen r22 suite (the R05 predicate line is unchanged), not introduced by r23.

## 3. The r22 source fixture behind R05 (the 'drop' arm)

`.ufo/waves/round-22/frozen/fixture-builder-v2.py:79`:

```python
if variant=='drop': result['hits']=result['hits'][:-1]
```

The `hits` list is built in `files` dict insertion order (`fixture-builder-v2.py:46-56`:
`policy.json`, `allowed.txt`, `unallowed.txt`, `non-author.txt`, `binary.bin`), and
`binary.bin` is NUL-skipped. Therefore `hits[:-1]` removes the **last** identity.

I read the actual committed-instance fixture bytes produced by the sealed driver
(`/fast/scratch/hyaku/mori-r23/MeasureDriver/measure-measure4/c1/after-fixtures/drop/receipt.json`,
synthetic metadata only) and confirmed the derived fact directly:

* receipt inner `hits` = `policy.json:13, allowed.txt:1, allowed.txt:2, unallowed.txt:1` → **4**
* receipt inner `allowlisted_hits` = 3, `unallowlisted_hits` = 1, `non_author` = **1**
* the tool's own recomputed partition (measured evidence) = `policy_excluded_hits` =
  `non-author.txt:1`, `scanner_hits` = `allowed.txt:1, allowed.txt:2, policy.json:13,
  unallowed.txt:1` → raw **5**, scanner **4**

So the dropped identity is **`non-author.txt:1` — the policy-excluded (non-author) identity**,
which lives in the receipt's raw `hits` list and in **no** partition list. It is the one
identity whose disappearance is invisible to `allowlisted_hits`/`unallowlisted_hits` and to the
`metric`/`non_author` counters.

**Concrete counterexample (bounded) — what R05 does catch.** The receipt's remaining 4 hits are
*exactly* the set the tool recomputes as `scanner_hits`. An implementation that compared
`receipt['hits']` against the **scanner partition** instead of the **raw scan population**
would find the two multisets equal (`Counter` comparison is order-insensitive; the sets differ
only in ordering), would record **no** difference, and would exit **0** `RETENTION_RECONCILED`.
R05 would then be **red** (`expected_exit=1`). R05 is therefore a genuine discriminator of
*raw-population vs scanner-partition comparison* — the correction the r22 denominator note
made, and the reason 'drop' was chosen.

## 5. Findings

### F1 (medium, inherited from the frozen r22 suite) — R05 alone does not force recomputation; concrete counterexample

The 'drop' receipt is **internally inconsistent**: it claims `non_author:1` while its own `hits`
list contains **zero** non-author identities (4 hits vs `3 allowlisted + 1 unallowlisted +
1 non_author = 5`). I verified this arithmetic directly on the fixture bytes (§3).

Therefore an implementation that never scans the committed tree and only cross-checks the
receipt's fields against each other — specifically `len(hits)` vs
`len(allowlisted_hits)+len(unallowlisted_hits)+non_author` — would still flag this receipt and
return exit 1 / `RETENTION_RECONCILIATION_MISMATCH`, **passing R05 without performing the
recomputation the capability exists for**.

Bounding (important, and why this is *not* a C1 regression): the counterexample is bounded to
**R05 in isolation**. The 26-arm suite pins recomputation jointly — R03 requires
`(raw_total, policy_excluded, scanner_total) == (5,1,4)` and R04 requires the exact
`scanner_hits` identity list on the *valid* arm, neither of which an echo-only implementation can
fabricate. The r23 contract explicitly keeps R01–R24 as the r22 frozen v2 predicates
(`contract.md`, C1 bullet 1), so this weakness is inherited, not introduced; changing it would
mean editing frozen expectation bytes, which is forbidden.

### F2 (low) — R05 pins exit/finding/stderr only; the mismatch-path diagnostics are unpinned

`record('R05','drop',1,'RETENTION_RECONCILIATION_MISMATCH')` attaches no predicate, so an
implementation that exits 1 with the right `finding_id` but reports `differences: []`,
`receipt_match: true`, or receipt-echoed counters on the exit-1 path would still pass R05.
The *measured* tool does not do this (it reports `differences:['hits']`, `receipt_match:false`
and recomputed counters — §4), so this is a coverage limit of the frozen requirement, not an
observed defect. R05–R10 share this shape.

### F3 (low) — R05's discriminating power is the *only* thing 'drop' buys, and it is fragile to
receipt-writer changes

R05 discriminates raw-population vs scanner-partition comparison *because* the dropped identity
is the non-author one. If a future receipt writer emitted `hits` already partitioned by the
policy glob, 'drop' would remove a partition-visible identity and the arm would lose that
discriminating power (it would then only test a length/cardinality check). The frozen fixture
builder is byte-pinned, so this is a forward-looking coupling note, not a present defect.

### F4 (informational, non-defect) — exit-1 vs exit-2 precedence is exercised and stable

R05 requires exit 1, so the 'drop' receipt must reach the population comparison rather than
being rejected earlier as a setup error. The 'drop' receipt is well-formed (4 distinct hits,
all fields typed, `must_redact_paths: []`), so `normalize_hits` does not raise
`duplicate_receipt_hit` and the run reaches `:224-232`. Confirmed by the observed exit code `1`
and `differences:['hits']` — and by the r22 suite's separate `duplicate` arm (R19) which is
pinned to exit 2. The two arms together pin the precedence empirically; no ambiguity is left
open *in the frozen suite*.

## 6. R25 (API cutover) vs the unchanged semantic requirements — the distinction

| | R25 | R05 (and the other 24) |
|---|---|---|
| predicate text | `oracle-rename.py:75-80` (inserted at index 24): every parsed oracle run has `schema == 'mori-retention-reconciliation-v2'` and no `raw_unallowlisted` key | `oracle-rename.py:55` — byte-identical to r22 `oracle-reconcile-v2.py:51` |
| reads the renamed field? | **yes** (that is its whole content) | **no** — mentions no output key at all |
| before (entering tool, v1) | `pass=False` (`misleading_alias_runs=8`, `schema_v2_runs=0/18`) | `pass=True` |
| after (pinned tool, v2) | `pass=True` (`misleading_alias_runs=0`, `schema_v2_runs=18/18`) | `pass=True` (unchanged) |
| what it certifies | the *API surface* moved (schema string v1→v2, alias key gone, no compatibility alias) | the *semantics* (population recomputation, partition comparison, exit/finding mapping, setup-vs-mismatch precedence, privacy_clearance=false) are unchanged |

The R02/R11/R12 substitutions in the r23 oracle are a *third* category, and I checked them
against the entering source: in the entering file, `raw_unallowlisted` and
`scanner_unallowlisted` are **the same expression** `len(unallowed)` (line 234 of the entering
source), so substituting one for the other in those three predicates is value-preserving and
does not silently change the expected 1/3/1. R05 is not in that group and never was.

Consequently: **the "26/26 after, 25/26 before" headline is driven entirely by R25**; the
other 25 ids — R05 included — are red-to-red-free *carriers* of the no-harm claim for the
semantics, and the source-delta guard (§4) is what actually certifies that the C1 change was
a pure two-token edit rather than a semantic edit dressed as one.

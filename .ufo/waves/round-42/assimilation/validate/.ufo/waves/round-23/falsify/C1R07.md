## Concrete counterexample attempts (why the bounded agree is not blanket)

I tried to break R07 after the cutover; each route is closed by a specific, cited fact:

1. **Trust the receipt instead of recomputing** (tool would then not see the corrupted digest):
   closed by `:143-157` `scan()` + `:207` — the tool rescans the committed tree and recomputes
   every `line_sha256`; the receipt is only the *claim* side (`:201`).
2. **Drop `line_sha256` from the identity** (corruption becomes invisible): closed by `:121`
   `hit_key` = `(path, line, class, line_sha256)`, used at `:225`.
3. **Corrupted digest trips a type/shape validation → setup error (exit 2) instead of mismatch
   (exit 1)**: closed — `'0'*64` matches `SHA` (`:21`, `[0-9a-f]{64}`), `line` stays `13`
   (int > 0), the field set is unchanged, so `normalize_hits` (`:124-133`) accepts it; the arm
   therefore reaches the comparison, not the `Invalid` path (`:286-287` → exit 2
   `RETENTION_RECONCILIATION_SETUP`).
4. **The removed alias key perturbs the comparison or the finding selection**: closed by the byte
   identity above — the alias key existed only as an output field (`:234`); `differences` is built
   at `:224-230` and the finding/exit at `:231`/`:241`, both untouched. My re-derivation yields
   `differences == ['hits','allowlisted_hits']` for the digest arm and for no other reason.
5. **The oracle does not actually reach the `digest` arm** (e.g. a variant-name typo making R07
   a silent pass on the `valid` arm): closed by the recorded run list — the `digest` arm has its
   own fixture with its own `expected_receipt_sha256`, and the recorded digest-run stdout carries
   `receipt_match:false` with `differences ["hits","allowlisted_hits"]`, which the `valid` arm
   never produces (`receipt_match:true`).

## Residual risk, limits and verification gaps

1. **R07 alone is a one-bit predicate** (`exit 1` + `finding_id` + empty stderr). Any tool that
   answered `RETENTION_RECONCILIATION_MISMATCH` for *every* input would satisfy R07. R07 is not
   self-sufficient evidence; it is bound only in aggregate with R01–R04 (which require exit 0 on
   the `valid` arm and pin `raw_total/scanner_total/scanner_hits`), R24 (which pins
   `tool_sha256`, `inputs_sha256`, `input_revision`, `measured_revision`), and R25/R26. My
   agreement is therefore stated **for R07 as part of the 26-requirement aggregate**, and the
   aggregate's green is the driver's recorded observation, which I did not reproduce.
2. **My verdict is static.** Per the seat instruction I did not execute the tool, the fixture
   builder, the oracle, the driver, or the selftest. The runtime evidence in §A3 is quoted from
   `evidence/measure4/`; I re-derived the same values independently in memory but did not
   regenerate the runs.
3. **R07 does not cover the setup-error class.** R13–R21 exercise exit 2 `SETUP`; R07 only covers
   the mismatch class. A defect that turned a legitimate setup error into exit 1 MISMATCH would
   not be caught by R07 (R13–R21 would catch it). This is a property of the frozen requirement
   set, not of the cutover.
4. **The source-delta guard constrains one file only.** `frozen/c1-source-delta.json` covers
   `tools/mori-retention-reconcile.py`. It says nothing about other files, and the r23 driver's
   `tools_delta` check records the expected delta `reconciler M, quota A` — verified in
   `summary.json` (`expected == observed`).
5. **The round's strict red is not in C1.** The two failing checks in `measure4/summary.json` are
   C2 checks ("after the cutover every sealed case must match exactly" and "the sealed C2 oracle
   with `--real-expected` must report no unmet real-control requirement"), i.e. the frozen
   `CaseEscapedSpace` contradiction. C1 checks in the same summary all pass. Nothing in the frozen
   `CaseEscapedSpace` row touches R07, and the quota selftest arm (49/49, separately corrected
   fixture input) is a different tool (`tools/mori-quota-surface.py`) with no shared code path with
   the reconciler.
6. **Declared r22-side consequences are out of R07's scope and remain open by design:** r22's
   `oracle-reconcile-v2.py` R02/R11/R12 read the removed key, `measure-round22.py`'s output
   whitelist still names it, `round-22/frozen/expected-real.json` pins `"raw_unallowlisted": 4`,
   and five `refinement-reconcile.py` cases read the old key. R07 is in none of those sets.

# C3 operability critique

## Verdict and axes

Axes reviewed: (1) falsifiability of the claimed operability behavior, (2) before/after score comparability, (3) binding/provenance from the committed dispatch artifact to the actual task-tool request, and (4) detection of missing or malformed attempts.

C3 remains falsifiable as a **new ledger capability**: the frozen predicate can reject an existing row whose recorded digest/length/count disagrees with the dispatch artifact, or whose row ordering/final-started constraints fail (`frozen/c3-ledger-format.json:4-19`; `contract.md:39-43`). It is not a comparable before/after effectiveness measure. The baseline consists of different, legacy attempt receipts; all lack the new payload identity and so are counted unbound by construction. A post value of zero would establish adoption/self-consistency of the new format for the rows supplied, not a reduction in delivery errors in a stable population.

Score C3 as **capability acquisition**, not “9 unbound before → 0 after” improvement or a percentage reduction. Report the legacy baseline separately (9/9 rows structurally unbound), then a round-18 pass/fail on the narrower, evidenced property. Unless a trusted invocation receipt and completeness source are added, score only “committed dispatch artifact matches ledger,” and mark actual task-tool receipt/completeness as unproven. C3 is directly impacted; no C1 privacy or C2 freeze-order conclusion follows from this finding.

## Evidence and counterexamples

- `contract.md:39-43` defines the before set as round-17 wave1/wave2 legacy receipts and the after set as round-18 ledgers. `frozen/c3-ledger-format.json:20` repeats those as the metric populations. They are separate rounds/runs and the old shape lacks the new digest; the count is therefore a schema-adoption contrast, not a matched behavioral counterfactual.
- The frozen-base receipts were read with `git -C /home/vgpnk/Projects/shokunin/mori-shokunin show d005cdde0e009dea6c0cc29b37163de536528658:.ufo/waves/round-17/wave1-dispatch-attempts.json` and the corresponding `wave2-dispatch-attempts.json` (combined command exit 0). Wave 1 has 5 rows (`.ufo/waves/round-17/wave1-dispatch-attempts.json:1-23`); wave 2 has 4 (`.ufo/waves/round-17/wave2-dispatch-attempts.json:1-17`). Their fields are legacy `at`/`refused` (and one `result`); there are no payload digests. Thus the stipulated 9 unbound rows measure absence of the new field, not demonstrated failure to send the intended task payload.
- `frozen/c3-ledger-format.json:4-5,19` computes identity from canonical JSON of `taskCall.context` and `taskCall.tasks`, then recomputes that identity from `dispatch_path` at the measured revision. This binds those **committed fields** to the row. It does not observe the arguments at the task-tool boundary. The schema has no invocation-bound receipt or independent expected-attempt inventory. [INFERENCE] If L1 commits dispatch object P, records hash(P), then passes a modified P′ to the task tool while retaining the ledger for P, the specified verifier still sees only P and the ledger and will accept them. It therefore cannot prove that the tool received P. The frozen `known_limit` acknowledges the copy boundary (`:21`), but the claim/score must preserve that limit.
- The identity is also a projection, not a digest of every field received by the task API: it includes only `context` and `tasks` (`frozen/c3-ledger-format.json:4`). The task-tool interface has an `i` argument, which is not part of this projection. If that argument is material to the invocation identity, it is not bound either.
- A concrete omission counterexample follows from the predicate: an actual refused call followed by a started call can be represented by a ledger containing only the started call, renumbered as attempt 1, with matching digest/length/count. The supplied row is contiguous, the sole started row is last, and its `started_ids` can equal `tasks_count`; nothing in `:19` compares the ledger against an independent call count. [INFERENCE] The specified verifier will call this clean even though one refusal was omitted. The same gap permits omission of an entire wave if the caller simply never supplies that ledger: the command interface is one `--ledger PATH` at a time (`contract.md:66-69`), with no required wave manifest.
- `started_ids` is only a count (`frozen/c3-ledger-format.json:17,19`), not the returned ID set. The claim at `:21` that returned IDs match the registry is not enforced by the frozen verify rule. A wrong ID set of the right size is indistinguishable to this predicate. Further, the predicate does not explicitly require every non-started result to be `refused`, or require the stated `refused_text` semantics (`:15-19`).
- A coordinated edit to both the committed dispatch payload and its ledger digest/length/count is internally consistent under `:19`; without an independent trusted dispatch/call receipt, there is no expected digest to compare against. [INFERENCE] This is outside the current verifier's evidence boundary, even if a one-sided payload mutation is caught.

## Falsifier L1 must run

Add and run two negative mutation arms against the implemented `verify` (do not count a happy-path selftest as covering them):

1. **Call-boundary divergence:** retain dispatch artifact P and a ledger row correctly bound to P, but have a test call-boundary recorder observe P′ (change one byte in `context` while keeping `tasks_count` unchanged). Assert `verify` fails specifically for call-payload mismatch. If there is no boundary receipt to compare, record this as a demonstrated limitation and narrow C3 to artifact self-consistency; do not score task-tool receipt binding as passed.
2. **Omitted refusal:** give the fixture an independent invocation record for a refused attempt followed by a started attempt, then remove the refusal from the ledger and renumber the started row. Assert `verify` fails for a missing attempt. If the tool has no independent invocation record/expected count, the current format cannot express this falsifier; record that absence and do not claim complete per-attempt coverage.

Also mutate the returned ID set while preserving its count if registry agreement is retained as a claimed condition; the current row schema/rule must reject it or that claim must be removed. These are proposed tests, not runs performed here.

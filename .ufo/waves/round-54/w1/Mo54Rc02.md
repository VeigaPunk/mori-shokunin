## Things a careless reader might miss (per row)

- Rows 1–2: the claim "the read never sums the deltas" does not mean mode-2 enforcement uses a
  permanently stale value — `percpu_counter_sync` exists (percpu_counter.c:146, header decl at :62)
  and row 6 shows it is invoked on every CPU when switching to mode 2. `read` is cheap/approximate,
  `sum` is exact; both are still separate primitives in v7.3 (SMP branch — the file is unchanged, so
  the non-SMP fallback at header lines ~247–268 is also unchanged).
- Rows 3–5: `mm_init.c` shows a ~370-line diff (KHO scratch-migratetype work, mirrored-kernelcore /
  overlap_memmap_init removal, sparse/memmap init moved into `mm_core_init_early`,
  `free_area_init_core_hotplug` returning `int`, `__init_page_from_nid`/`overlap_memmap_init` deleted).
  A careless diff-reader could conclude `mm_compute_batch` moved or changed; in fact its whole body
  (v7.3 195–215) is byte-identical and merely shifted +4 by the new `#include` block at lines 36–41.
  The claims pin CPU-count basis (`num_present_cpus`) and formula — all stand.
- Row 5: the claim says "the batch … is RAM pages divided by CPUs and by 256, capped at INT_MAX".
  Strictly, that formula produces the intermediate `memsized_batch`; the installed
  `vm_committed_as_batch` is `max_t(s32, memsized_batch, batch)` (line 214), i.e. additionally floored
  at `max(2·nr_cpus, 32)` — the floor row 3 covers. Read together the table is complete; read alone
  row 5 omits the floor. Same text as v7.2, disposition still `holds`.
- Row 6: `mm_compute_batch(new_policy)` runs on EVERY `overcommit_memory` write (any target mode);
  only the per-CPU sync is gated to `OVERCOMMIT_NEVER`. The claim's "switching to mode 2" phrasing is
  fine for the sync, and recompute-on-any-write is a superset of mode-2 writes — nothing falsified,
  but the unconditional recompute is easy to misread as mode-2-only.
- Rows 7–8: the proc/meminfo side of row 7 was verified only by fetching `fs/proc/meminfo.c?h=v7.3`
  (not a ledger copy); it confirms `Committed_AS` still comes from `vm_memory_committed()`. The
  distinction the entry draws — approximate `read_positive` for enforcement (line 994) vs exact
  `sum_positive` for reporting (line 938) — survives intact.
- The `mm_init.c` `mm_compute_batch` callers are unchanged: `mm_compute_batch_init`
  (`mm_compute_batch(sysctl_overcommit_memory)` at boot, v7.3 231) plus the hotplug notifier on
  `MEM_ONLINE`/`MEM_OFFLINE` (v7.3 219–227). The batch still recomputes on memory hotplug.

## Row 19 — h=4f693eb5f736 — S524 memory-failure-trace.h.v7.3

Claim: "The tracepoint belongs to the ras trace system for historical reasons, so it is
enabled as ras:memory_failure_event and not under oom."

Context (copy, lines 2-8 and the event definition at line 74):

```text
#undef TRACE_SYSTEM
/*
 * For historical versions, memory_failure_event is in ras subsystem,
 * some user programs depend on it.
 */
#define TRACE_SYSTEM ras
```

plus `TRACE_EVENT(memory_failure_event, ...)` at L74.

Judgement: "for historical reasons" faithfully paraphrases the comment's historical-
compatibility statement (the wording in this committed copy is "For historical versions" —
likely an upstream typo for "reasons", but it carries the same historical-compatibility
meaning, reinforced by "some user programs depend on it"). `TRACE_SYSTEM ras` +
`TRACE_EVENT(memory_failure_event)` puts the event under the ras system in exactly one
place, so it is enabled as `ras:memory_failure_event` — and a single TRACE_EVENT under
`ras` entails "not under oom" (the file defines no second system; a trace event belongs to
one system). Fully supported.

## Row 20 — h=8248e6d24be8 — S524 memory-failure-trace.h.v7.3

Claim: "The traced line repeats the page type and outcome strings of the logged recovery
line after the pfn, so traced and logged outcomes can be matched."

Judgement: OVERCLAIM on "repeats the page type ... strings". The two string tables in the
committed v7.3 copies diverge on one page type:

- S524 memory-failure-trace.h.v7.3 L49: `EM ( MF_MSG_ALREADY_POISONED, "already poisoned" )`
- S521 memory-failure.c.v7.3 L897: `[MF_MSG_ALREADY_POISONED] = "already poisoned page"`

Both are emitted for the same event: `action_result()` (S521 L1281-1298) calls
`trace_memory_failure_event(pfn, type, result)` at L1284 and then
`pr_err("%#lx: recovery action for %s: %s\n", pfn, action_page_types[type],
action_name[result])` at L1291-1292, while the trace prints
`TP_printk("pfn %#lx: recovery action for %s: %s", ... __print_symbolic(__entry->type,
MF_PAGE_TYPE), __print_symbolic(__entry->result, MF_ACTION_RESULT))` (S524 L93-97). For
MF_MSG_ALREADY_POISONED the traced type string ("already poisoned") does not repeat the
logged type string ("already poisoned page"), so a text match of the traced line's page
type against the logged line's strings fails for that type. The claim's payoff clause only
asks for outcome matching, and the four outcome strings are identical
(MF_IGNORED/FAILED/DELAYED/RECOVERED → "Ignored"/"Failed"/"Delayed"/"Recovered" in both
S524 L25-28 and S521 L871-876) — but the claim as written asserts the page-type strings
repeat, which the sources falsify for one of the twenty page types. The word that says more
than the source: "repeats the page type and outcome strings" — the page-type strings do not
all repeat.

## Row 21 — h=257f4acfda4e — S502 proc.rst.v7.3

Claim: "The meminfo field reports, in kilobytes for the whole host, how much memory the
kernel has marked as corrupted."

Context (copy, lines 1269-1271, plus the field example at L1100
`HardwareCorrupted:     0 kB`):

```text
HardwareCorrupted
              The amount of RAM/memory in KB, the kernel identifies as
              corrupted.
```

Judgement: "in kilobytes" = "in KB"; "marked as corrupted" = "identifies as corrupted".
"For the whole host" is entailed two ways: this is a field of /proc/meminfo — a
machine-wide memory report whose sibling fields (MemTotal, MemFree, Slab, …) are all
single host-wide totals — and the committed implementation copy S-meminfo
(`corpus/evidence/sources-r53/meminfo.c.v7.3` L136-139) prints the field from one global
atomic, `atomic_long_read(&num_poisoned_pages) << (PAGE_SHIFT - 10)`, i.e. one total for
the machine, not per node. Fully supported.
